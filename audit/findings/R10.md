## Independent re-verification of the docstring defect (not inherited)

`demo/lattice_app.py:998-1017`'s docstring states:

> *"sinh(2\*Kc) = 1, so Kc = arcsinh(1) = ln(1+sqrt(2)) and betac = Kc /
> j_max."*

Ran three independent checks, none copied from the controller's
pre-finding:

```
SymPy, this task:
  Kc_code   = ln(1+sqrt(2))/2       -> sinh(2*Kc_code)   = 1.00000000000000000000000000000  (exact, 30 digits)
  Kc_docstr = ln(1+sqrt(2))         -> sinh(2*Kc_docstr)  = 2.8284271247461900976            (NOT 1)
  arcsinh(1) == ln(1+sqrt(2))  ?  True
  Kc_code == arcsinh(1)/2      ?  True

Wolfram|Alpha (third-party, this task, live query via audit/oracles/wolfram.py):
  N[log(1+sqrt(2))/2, 20]      -> 0.44068679350977151262
  N[ArcSinh[1]/2, 20]          -> 0.44068679350977151262
  N[sinh(2*log(1+sqrt(2))/2), 20] -> 1.0000000000000000000

Python (the actual code path):
  math.log(1.0+math.sqrt(2.0))/2.0        = 0.44068679350977147
  math.sinh(2 * that)                     = 0.9999999999999999
```

**Independently confirmed: the CODE is correct** (`return
math.log(1.0 + math.sqrt(2.0)) / 2.0 / j_max`, `:1017`, correctly divides
by 2) **and the DOCSTRING is wrong** -- substituting the docstring's own
claimed value (`Kc = ln(1+sqrt(2)) = 0.8814`) into the docstring's own
stated defining equation (`sinh(2*Kc) = 1`) gives `2.828`, not `1` -- the
docstring's claim fails its own equation, independent of even knowing the
correct answer. `sinh(2*Kc)=1` implies `2*Kc = arcsinh(1)`, hence `Kc =
arcsinh(1)/2 = ln(1+sqrt(2))/2`; the docstring drops the `/2`. Three
independent computations (SymPy, Wolfram|Alpha, and the literal running
Python of the function itself) agree the CODE's constant
(`0.44068679350977...`) is the one that actually satisfies Onsager's
condition. **This re-verifies `audit/findings/R10-controller-prefinding.md`
from scratch and confirms it in full**, including that the defect is
docstring-only -- the `return` statement, the on-screen ratio, and every
number the app displays are unaffected.

## The harder question: is displaying `beta/beta_c` defensible at all?

Two considerations neither A2 nor the controller's pre-finding raised,
found by pushing further on "what does Onsager actually require":

**Onsager's result is not just "uniform coupling, no field, infinite" --
it is specific to the standard NEAREST-NEIGHBOUR square lattice, degree
4.** `sinh(2K_c)=1` is the critical condition for the coordination-4 square
lattice specifically; it is not a general formula that degrades gracefully
as connectivity increases. Z1's topology (`target.py`'s `degree=16`, the
`(1,0),(2,1),(2,3),(4,1)`-rotation offset rules) is not "a square lattice
with some extra non-idealities" -- it is a DIFFERENT GRAPH with 4x the
coordination number of the one Onsager solved. Basic mean-field intuition
(more neighbours reinforce alignment more easily) says a real critical
coupling for a degree-16 graph would sit substantially BELOW the
degree-4 Onsager value at the same `beta`, i.e. this graph should order
"more easily" than Onsager predicts -- the sign of the error, not just its
existence, is knowable in principle and is not stated. `ONSAGER_ASSUMPTION_NOTE`'s
phrase "the graph is not a plain square lattice" is TRUE but reads as one
item in a list of three roughly-equal caveats (non-uniform couplings,
hidden mediators, wrong graph) when it is arguably the largest single
departure from the theorem's hypotheses, not a peer of the other two.

**Combined with the 2.85x mediator-inclusion sensitivity (I-1) and the
docstring defect (both independently reconfirmed above), the number
carries three independent, compounding sources of imprecision that are
each real but none of which is individually fatal, while the caveat text
treats them as one undifferentiated disclaimer.** None of the three make
the number FALSE -- `beta/beta_c` genuinely is what it claims to be,
`beta / onsager_betac(j_max)` for the `j_max` actually used, computed
correctly. The question is whether "genuinely what it claims to be" is
enough when what it claims to be is this far from what a reader will
assume "beta over the critical beta" means physically.

### Recommendation

**Keep displaying it, but strengthen the caveat rather than remove the
number.** Reasoning:

1. The number is not fabricated, not silently substituted, and its formula
   is independently verified correct (SymPy, Wolfram|Alpha, and the code
   itself all agree). Removing a correctly-computed, honestly-labelled
   orienting estimate is a stronger reaction than the evidence warrants --
   this project's own stated ethos (compute from the formula, never
   hardcode, disclaim what is uncertain) is exactly what `onsager_betac`
   already does at the code level.
2. But "ORIENTING estimate" currently undersells how far this sits from a
   textbook `beta/beta_c`: three compounding, independently-confirmed
   sources of departure (wrong coordination number, mediator-inclusion
   sensitivity of 2.85x, and -- now fixed by this task's own record, see
   below -- a docstring that would have mis-taught the formula to the next
   person who tried to verify it) make this closer to "a suggestively-named
   number in the right ballpark" than "an estimate with known, bounded
   error." A caveat that lists qualitative reasons without any of the
   three quantitative facts this task surfaced (2.85x sensitivity; 4x
   coordination-number mismatch; which `j_max` is actually used) will not
   survive being screenshotted without its caveat -- exactly the risk this
   task was asked to judge. A number this caveated but this liable to be
   quoted bare needs the SPECIFIC magnitudes in the caveat, not just the
   categories of concern.
3. **Concrete, minimal strengthening (Phase F candidate, not performed
   here):** state the mediator-inclusion sensitivity NUMERICALLY next to
   the ratio (e.g. "workload-only alternative: beta/beta_c={2.27}" as a
   second number, not just a comment), and change "not a plain square
   lattice" to name the actual coordination-number mismatch ("degree 16 vs.
   Onsager's degree 4"). This keeps the number, keeps it honest, and closes
   the specific gap this task found between what the caveat says and what
   a reader needs to not be misled.

**Verdict: the docstring defect is CONFIRMED (independently, from scratch,
by three separate methods). The displayed ratio is not wrong, but its
caveat is thinner than the number's actual fragility warrants. This
section recommends keep-with-strengthened-caveat, not remove, and not
leave as-is.**
