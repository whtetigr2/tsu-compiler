# R14 -- Numerical stability, adversarially (Wave 2)

**Method:** every check below hits a genuinely **public** entry point
(importable and callable from outside its own module, not a
leading-underscore private helper) directly, deliberately bypassing the
full spec/encode/compile pipeline -- because `validate_coefficient_scale`
(called from `encode()`) already guards the **only** value the real
`compile_spec()` pipeline can ever hand to `beta` (`beta = spec_beta(spec) /
coefficient_scale`, always finite and `> 0`, `search.py:161,391`), but
`lower()`, `route.insert_mediators`, `thrml_backend.*`, `tsu.ess.*`, and
`demo.lattice_app.energy_of_draw` are all independently importable and
callable with values the front door's own guard never reaches (a
hand-edited receipt JSON, a future caller, a test, a REPL). Script:
`audit/r14_numerical_stability_check.py`, run with the project's pinned
interpreter, 39 checks, output reproduced/summarised below. Every result is
classified into exactly one of three buckets, per the plan's own
instruction that these are not equally acceptable: **CRASH** (an exception
propagates uncontrolled), **SILENT WRONG ANSWER** (returns without
complaint, but the number is `NaN`/`inf`/nonsensical), or **HONEST
UNAVAILABLE** (a labelled `unavailable: ...` / a clearly-named guard
exception, before a number is produced).

## 1. Beta near zero and very large

- `beta in {1e-12, 1e-6}`: `src/tsu`'s `exact_distribution` (thrml's own
  `jax.nn.softmax`, internally max-shifted) and the audit's own oracle
  (`exact_boltzmann`, bare `math.exp`, **not** max-shifted -- see
  `oracles/exact.py`'s own arithmetic) agree to `2.776e-17`. OK.
- `beta in {1e6, 1e12, 1e300}`: **`src/tsu`'s own `exact_distribution` stays
  numerically stable and correctly normalised at every one of these**
  (`sum(probs)=1.000000` in all three cases) -- `jax.nn.softmax`'s internal
  max-shift genuinely protects it, confirmed live, not assumed.
  **The audit's own `exact_boltzmann` oracle crashes with `OverflowError:
  math range error` at all three** (`beta=1e6, 1e12, 1e300`), because it
  computes `math.exp(-beta*e)` directly with no shift. **This is a
  numerical limitation of the audit's own oracle (`audit/oracles/exact.py`),
  not a defect in LATTICE** -- recorded here in full because misattributing
  a crash to the wrong codebase would itself be exactly the kind of error
  this audit exists to catch; see "Recommended, non-`src/tsu` scope" below.
- `beta=0.0` exactly: `exact_distribution` produces the uniform distribution
  over all `2**n` states to `0.00e+00` deviation, matching `p ~ exp(0) = 1`
  for every state, as required. OK.
- `beta <= 0` (`demo/scope.py`'s `beta_to_temperature`): correctly refuses
  with a `ValueError` naming the reason, for `beta in {0.0, -1.0, -1e300}`.
  HONEST UNAVAILABLE, all three.

## 5. NaN / Inf ingress at public entry points -- the substantive findings

- `oracles.exact.exact_energy`: an out-of-domain state entry (`2`, `NaN`,
  `inf`) is correctly rejected with a `ValueError` naming the bad value, in
  all three cases tested. HONEST UNAVAILABLE (this module's own guard
  behaves exactly as designed under attack).
- `oracles.exact.exact_boltzmann` with `NaN` inside `b`: correctly caught
  by the module's own `Z`-usability guard (`Z=nan` -> `ValueError`).
  HONEST UNAVAILABLE.
- `tsu.ess.effective_sample_size` on a chain containing one `NaN` entry: the
  chain's per-chain variance becomes `NaN`, correctly caught by the
  existing `not np.isfinite(var)` guard (`ess.py:219`) and reported as
  `unavailable: series is constant (zero variance); autocorrelation is
  undefined` -- the reason text is slightly imprecise (the series is not
  actually *constant*, it is *NaN-contaminated*; both trip the same `not
  np.isfinite(var) or var <= 1e-300` branch and share one message) but the
  **effect** is correct: no NaN-contaminated number is ever returned as a
  real ESS/tau. HONEST UNAVAILABLE, with a Minor labelling-precision note
  filed below.
- **`lower()` performs no validation on a term's `weight`, and none on
  `EnergyModel.beta`.** A `Linear` term with `weight=NaN` lowers
  successfully with **no error, no warning**, into an `IsingModel` whose
  `biases`, `weights`, and `offset` all contain `NaN`
  (`biases=[nan, -0.25]`, `weights=[-0.25]`, `offset=nan`). Feeding
  `EnergyModel.beta = NaN`/`inf`/`-inf` similarly lowers into
  `IsingModel.beta` unchanged and unvalidated; `exact_distribution` fed
  that model then also returns `probs=[nan, nan]` -- a "successfully
  compiled," self-consistently propagating NaN all the way through, never
  flagged. **SILENT WRONG ANSWER**, both sub-cases.
- `demo.lattice_app.energy_of_draw` fed a row containing `NaN`: returns
  `NaN` with no guard and no exception. **SILENT WRONG ANSWER.**
- `route.insert_mediators` fed a `NaN`/`inf` coupling **on the edge that
  actually gets mediated** (deliberately placed there -- see the script's
  own note on why the edge index matters: a triangle's own BFS-parity
  colouring mediates only one specific edge, and a bad value on a *kept*
  edge would test nothing about the mediation arithmetic): `math.acosh
  (math.exp(2*beta*|J|))` with `|J|=inf` produces `A=inf`, propagated into
  the mediated model's weights and a `NaN`/`inf` `offset`, with **no
  exception at any point**. **SILENT WRONG ANSWER**, both `NaN` and `inf`.
  A bad value on a **kept** (non-mediated) edge, tested side by side,
  passes through completely untouched -- expected, since no arithmetic at
  all is applied to a kept edge, but recorded as a distinct mechanism from
  the mediated-edge case (same bucket, different cause).

## Findings

### Important

**N-1: `lower()` performs no validation on a spec term's `weight`, or on
`EnergyModel.beta`; a `NaN`/`inf` value in either silently produces a
"successfully lowered" `IsingModel` carrying `NaN`/`inf` biases, weights,
offset, or beta, with no error and no `unavailable:` label anywhere.**
`src/tsu/passes/lower.py` (both `_lower_dense` and the real `lower()`) --
confirmed at `lower.py:44-342`, no `isfinite`/`isnan` check appears
anywhere in the file. Compare `encode.py`'s own `validate_coefficient_scale`
(`encode.py:367-396`), which explicitly documents and guards against
exactly this failure class ("NaN or infinite would produce NaN/infinite
coefficients ... every one of these would still look like a successful
compile while the result is garbage") for `coefficient_scale` specifically
-- the same discipline is not applied to a raw term weight or to `beta`
itself at the one layer (`lower()`) that turns them into the numbers a
sampler will actually use. **Concrete failure scenario:** a future term
generator (a new spec construct, a bug in an existing one, e.g. a division
by an edge count that can be zero) produces a `NaN` or `inf` term weight;
`lower()` accepts it silently, `insert_mediators`/`thrml_backend` propagate
it silently (see below), and the receipt is written as `verdict=COMPILED`
with a model that samples uniformly-garbage or crashes deep inside JAX with
no diagnostic pointing back to the actual defective term. **Reachability
caveat, stated honestly:** the ONLY beta value `compile_spec()`'s own
pipeline can currently produce is always finite and positive (guarded
transitively via `validate_coefficient_scale`), so this specific `beta`
sub-case is not reachable through the front door today -- but term weights
are never validated by that guard at all (only `coefficient_scale`, the
uniform multiplier, is), so the weight sub-case has no equivalent front-door
protection. **What was checked:** direct injection of `NaN`/`inf`/`-inf`
at both injection points, on a real `lower()` call, with the resulting
`IsingModel` fed onward into `exact_distribution` to confirm the
propagation is not caught downstream either.

**N-2: `route.insert_mediators`'s gadget-coupling formula (`A =
acosh(exp(2*beta*|J|))/(2*beta)`) performs no validation on `J` and
silently propagates `NaN`/`inf` into the mediated model's weights and
`offset` when the affected edge is one that gets mediated.**
`src/tsu/passes/route.py:186-206`. **Concrete failure scenario:** the same
upstream defect as N-1 (a `NaN`/`inf` coupling reaching this pass) compounds
here: a mediated model with a `NaN`/`inf` edge weight AND a `NaN`/`inf`
`offset` is returned with `bipartite_after=True` and a normal-looking
`MediationReport` -- nothing in this pass's own return value signals that
anything is wrong. **What was checked:** the bad value was deliberately
placed on the specific edge this module's own BFS-parity colouring is
verified (by hand, and by the mediator-count reported) to actually mediate,
not an arbitrary edge -- a first draft of this check placed it on a **kept**
edge instead and found nothing, which would have been a false "no defect"
conclusion; the corrected placement is recorded in the script's own comment
specifically so this mistake is visible and not silently repeated.

### Minor

**N-3: `tsu.ess.effective_sample_size`'s `unavailable` reason text says
"series is constant (zero variance)" for a chain that is actually
NaN-contaminated (not constant) -- the guard's *effect* is correct (no
NaN-derived number is ever returned), but the message is imprecise for
this specific cause.** `src/tsu/ess.py:218-222`: `var = chains.var(axis=1).
mean()`; `if not np.isfinite(var) or var <= 1e-300` catches both "genuinely
constant" (`var` a tiny finite number) and "NaN present" (`var` itself
becomes `NaN`, caught by `not np.isfinite`) under one shared message.
**Concrete failure scenario:** a developer debugging why ESS reports
`unavailable` on real sampler output would read "series is constant" and
look for a stuck/frozen chain, when the actual cause is a NaN that leaked
in from elsewhere (e.g. exactly N-1/N-2's own failure mode) -- the message
points at the wrong hypothesis. **What was checked:** a chain with exactly
one `NaN` entry among 200 otherwise-normal values, confirmed to trip this
exact branch and this exact message.

### Non-`src/tsu` scope (recorded for completeness, not a LATTICE defect)

**Audit-oracle-only: `audit/oracles/exact.py`'s `exact_boltzmann` raises
`OverflowError` around `beta ~ 1e5`-`1e6` (bare `math.exp`, no max-shift),
while `src/tsu`'s own `exact_distribution` (via `jax.nn.softmax`) remains
correct and stable up to `beta=1e300` on the same instance.** This is a
genuine numerical limitation of the audit's own reference implementation,
not of the code under audit -- recorded here in full, with correct
attribution, specifically because a hostile audit that crashed its own
oracle and misfiled the crash against LATTICE would be exactly the
misattribution failure mode this document's Epistemic Discipline section
warns against. Not filed as a LATTICE finding. If the oracle is ever reused
at extreme beta in a later wave, its own `weights = [math.exp(-beta*e) for
e in energies]` (`oracles/exact.py`) would need the same max-shift
`thrml_backend.py`'s `_edgeless_distribution`/`_edgeless_sample` already
apply (`x = x - x.max()`) before it could be trusted there.

### What was tried and did not turn up a finding

- `beta` near zero (`1e-12`, `1e-6`): both `src/tsu`'s path and the oracle
  agree and remain numerically well-behaved. No finding.
- `beta=0.0` exactly, and `beta<=0` via `beta_to_temperature`: both produce
  the theoretically correct result (uniform distribution; honest refusal,
  respectively). No finding.
- `J=0` (both the zero-weight-edge and fully-edgeless cases), including the
  edgeless model's separate `sample_chains` code path: both agree with the
  oracle and run without incident. No finding.
- Degenerate (fully flat) energy landscape: exactly uniform, as required.
  No finding.
- Empty valid set (`exact_boltzmann` with `n=0`) and single-state
  distributions (fully-clamped model, `n=1` spin): all handled correctly,
  either producing the mathematically correct single/degenerate
  distribution or an honest, precisely-worded refusal. No finding.
- `oracles.exact.exact_energy`'s own state-validation guard, attacked with
  an out-of-range integer, `NaN`, and `inf`: correctly rejects all three.
  No finding.
- Whether `diversity_reachable`'s division (`search.py`'s
  `task_validity = ok / len(got)`) could divide by zero if `got` (the raw
  sample batch) were ever empty: `got`'s size is fixed by
  `_VERIFY_SAMPLE_PARAMS["n_samples"]=200` (`search.py:513-514`), a
  positive compile-time constant with no live-configurable path to zero in
  the current codebase -- this division is unguarded but **not reachable**
  through any public entry point exercised by this audit. Not filed as a
  finding (nothing currently reaches it), flagged here only as a latent
  assumption a future refactor should not silently break.
