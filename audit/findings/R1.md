# R1 -- What is really executing

**Scope.** Confirm `dependency_map.md` (Task A1)'s claim that 5 of 12 architecture
arrows never fire live (`insert_mediators`, `place`, `route`, `search`, `torx`),
using a genuinely different instrumentation method, then answer plainly whether
presenting a nine-stage PIPELINE panel is honest when five of those stages do not
execute during live sampling.

**Method used here -- deliberately NOT `sys.settrace`.** A1 used a global
frame-event hook (`sys.settrace`) that watches every call event and classifies it
in/out of scope after the fact. This task instead used **monkeypatched sentinel
wrappers**: `audit/r1_sentinel_check.py` replaces the specific function objects
under question -- `insert_mediators`, `place`, `route`, every alias `search.py`
re-imports of those three plus `compile_spec`/`_compile_spec_impl`/`_verify`,
`torx_backend.torx_cross_check`, and seven of the real `torx` package's own public
constructors (`DFG`, `ChainFactor`, `TiledFactor`, `DeterministicFactor`,
`AbstractFactor`, `AbstractChainFactor`, `AbstractTiledFactor`, plus
`torx.psc.PISING`/`DiscretePCircuit`/`StateVectorSimulator`) -- with counting
wrappers **before the app runs at all**, then calls the identical two actions A1's
trace used (`SampleWorker._run_unclamped_tick` then `._run_clamped_batch`, same
receipt `demo/receipts/small`, same clamp `{"g0_0": 0}`, same `speed_idx=0`) and
reads the wrapper's own invocation count. This does not walk frames or classify
anything "in scope" after the fact -- a wrapped function's counter increments iff
that exact object is called, full stop. It also does not share `settrace`'s
JIT-opacity limitation (A1's own biggest methodological caveat), because a
monkeypatched wrapper fires on the Python-level call regardless of what happens
inside the wrapped function afterward, including a `jax.jit` boundary.

**Import-order care taken (recorded because getting this wrong would silently
produce a false "never called" result):** `insert_mediators`/`place`/`route` are
each re-imported BY NAME into other modules (`search.py`'s
`from .route import insert_mediators, route`; `place.py`'s
`from .route import ... insert_mediators`). A name-import binds a *new* reference
at import time; patching the defining module's attribute *after* a re-importing
module has already run its own `from ... import` would silently miss any call
routed through that module's own copy. `r1_sentinel_check.py` therefore imports
`route`/`place`/`search`/`torx_backend`/`thrml_backend` explicitly first, patches
**every** namespace holding a copy of each target symbol, and only then imports
`lattice_app` -- so `lattice_app.py`'s own
`from tsu.backends.thrml_backend import sample as thrml_sample` binds the
*wrapped* function. `tsu.simulate.simulate` and `search._verify` both import their
sampler / `torx_cross_check` via a **local** import statement inside the function
body, which re-resolves the module attribute on every call regardless of import
order -- confirmed correct by the results below (`simulate()`'s indirect call to
`sample_chains` was captured).

## Minor: a small arithmetic slip in `dependency_map.md`'s own prose

**`audit/dependency_map.md` line ~53** states the clamped trace's breakdown in
prose as *"5 valid, 12 contract-fail, 2 non-codeword"* -- `5+12+2=19`, one more
than the 18 total draws the same sentence and the trace's own `batch_summary`
(`"total": 18`) state. Reading `audit/traces/clamped_trace.json`'s
`pushed_messages` directly (`Counter(m["kind"] for m in pushed_messages)`) gives
`contract-fail: 11`, not 12 -- `5+11+2=18`, which is internally consistent. **This
is a transcription slip in A1's prose, not an error in the trace file itself or
in any code under audit** (confirmed above: this task's own independent rerun,
using the same seed, reproduced `contract-fail: 11` exactly). Recorded per this
task's brief ("prior comments... are evidence, not immunity") because a reader
citing dependency_map.md's prose without checking the underlying JSON would carry
the off-by-one forward.

## The honesty question: is a nine-stage PIPELINE panel defensible when five stages don't execute live?

**Verdict: yes, on the specific evidence available, with one Minor caveat.**

The PIPELINE panel (`demo/lattice_app.py:2388`) is not a case of a UI claiming
live execution it does not perform. Three separate things support this:

1. **The panel's own section title says so, prominently, not in a footnote:**
   `"PIPELINE  (compiled once, at load)"` (`lattice_app.py:2388`) -- this is the
   header text every viewer sees above the nine rows, not buried text.
2. **Every one of the nine rows renders a real, frozen number, never a live one.**
   `_populate_static_panels` (`lattice_app.py:2827-2838`) reads
   `durations = r.passes.get("pass_durations", {})` and renders
   `f"[x] {stage:<13} {fmt_duration(durations[stage])}"` for each of
   `PASS_ORDER = ("encode", "lower", "analyse", "gate_checks", "place", "route",
   "build_program", "regime", "verify")` -- `durations` is read once, from
   `passes.json`, at `Receipt.__init__` and never refreshed. This audit
   independently re-checked, beyond A1's own explicit list, that `lower.py` and
   `gates.py` (the `lower`/`gate_checks` stages -- not among the five A1 named,
   but two more of the panel's nine rows) also show **zero** call edges in
   *either* of A1's own captured traces (`audit/traces/{unclamped,clamped}_trace.json`,
   grepped for `passes/lower.py` and `gates.py` in `in_scope_call_edges` --
   0 matches in both files, both stages). So the panel's honest claim is in fact
   **stronger** than "5 of 9 rows are stale" -- every one of the nine displayed
   stages is frozen, exactly as the panel's own caption says.
3. **An explicit prose caption directly below the checklist states the scope of
   the claim in plain language:** *"Compilation (encode..verify) ran ONCE, when
   this receipt was written -- the durations above are that one run's own
   numbers, read from passes.json. Only SAMPLING re-runs per world; the pipeline
   itself is not re-executing."* (`lattice_app.py:2833-2838`).

**The Minor caveat:** the checklist's own visual idiom -- `[x] stage_name
duration`, one row per stage, top to bottom -- is the SAME idiom conventionally
used by installers and setup wizards to mean "this step just ran, in this
session, successfully." A viewer who has internalised that convention from
elsewhere and skims past the dim, 8-point caption text below the list (visually
de-emphasised relative to the `[x]` rows themselves -- `font=(MONO_FAMILY, 8)`
vs. the rows' `font=MONO`) could misread nine checkmarks, including one
labelled `place  201.351s`, as nine things that just happened. This is a real,
if modest, presentation risk given the checklist idiom's conventional meaning
elsewhere -- not a fabrication, and not severe enough to call the panel
dishonest, because the caption **is present and correctly worded**, just smaller
and positioned after, not before, the checklist it qualifies.
