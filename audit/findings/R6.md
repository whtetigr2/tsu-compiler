# R6 -- "Zero valid samples" must never become "proven impossible" (Wave 3)

**Method:** read every code path that can report zero valid draws, then
execute the real, public functions directly (`demo/lattice_app.batch_feasibility`,
`demo/lattice_app.composite_missing_layers`) with constructed adversarial
batches, and read the literal on-screen f-strings for the paths that have no
standalone function (the LAYERS panel's band-regenerate path,
`_on_band_regenerated`, `lattice_app.py:4339-4354`). Script:
`audit/r6_zero_valid_check.py` (run with the project's pinned interpreter;
output reproduced below). This covers every path the brief names: infeasible
clamps, a zero-valid batch, an INFEASIBLE layer, a composite with a missing
layer, and (separately, since the compile-time state machine also uses the
word "infeasible") an infeasible spec.

## Findings

### Important

**The two live "zero valid" code paths use asymmetric grammar, and the
weaker of the two ("no valid world satisfies these pins") is the more
commonly hit one.** `demo/lattice_app.py:973-984` (`batch_feasibility`,
feeding the base-clamp path used on every ordinary pin-click) returns the
sentence `"no valid world satisfies these pins -- {total} draws, 0 valid"`
for a zero-valid batch. Its main clause -- "no valid world satisfies these
pins" -- is grammatically a present-tense, unqualified claim ABOUT THE PINS
THEMSELVES ("satisfies", not "was found to satisfy" or "has satisfied in
{total} draws so far"); the evidentiary qualifier is appended after an
em-dash, outside the clause a skimming reader parses first, and the label
this text is wrapped in (`f"INFEASIBLE: {reason}"`, `:3576`) is itself a
strong, absolute-sounding word. **Concrete failure scenario:** a viewer
screenshots or reads aloud "INFEASIBLE: no valid world satisfies these pins
-- 180 draws, 0 valid" and reports "the tool says this configuration is
infeasible" -- technically defensible (the draw count is right there) but
exactly the "absence of evidence taken as evidence of absence" failure mode
this section exists to catch, because the sentence's grammatical subject is
the PINS, not the BATCH. Contrast this with the SEPARATE, independently
re-typed implementation for the LAYERS panel's band-conditioning path
(`lattice_app.py:4346-4351`, not the same function -- there is no shared
helper), whose string -- `"0/{total} draws valid under this conditioning"`
-- puts the evidentiary qualifier INSIDE the main clause and names the
batch, not the pins, as the subject. Both strings feed the identical
`"INFEASIBLE: "` prefix (`:3576` and `:3906`), so a viewer sees the SAME
strong word attached to two differently-hedged sentences depending only on
which panel happens to be open, for what is the same underlying event
(zero valid draws in a finite batch). **What was checked:** ran both real
functions/paths with the plan's own worked example (180 draws, e.g. a
sampler that drew 180 invalid worlds); confirmed the state is genuinely
transient, not sticky -- `lattice_app.py:3477-3483`'s own comment states
the reasoning explicitly ("A fresh valid draw under the CURRENT clamp is
direct proof that clamp is feasible -- don't let a stale 'infeasible'
verdict... keep showing") and `batch_infeasible` is unconditionally reset to
`False` the instant any valid draw arrives, so the code's BEHAVIOUR never
treats this as permanent; only the WORDING of one of the two paths reads as
more absolute than the state actually is. Existing tests
(`tests/test_lattice_app_logic.py:265-282`) assert only that `"0 valid"` and
`"{n} draws"` appear as substrings -- they do not guard against the main
clause reading as an unconditional claim, so a future edit could make this
worse without failing any test. **Not performed (Phase F candidate):**
reword `batch_feasibility`'s reason string to match the band-conditioning
path's more careful grammar (e.g. `"0/{total} draws valid under these
pins"`), and give the two paths one shared helper so they cannot drift
independently again (currently two independently-typed implementations of
the identical concept -- an R16-adjacent duplication risk, noted here only
because it is the direct cause of the grammar asymmetry, not re-litigated).

### Minor

**`CandidateState.HARDWARE_INFEASIBLE` (`src/tsu/states.py:12`) is one enum
name covering two epistemically different situations: a proven,
deterministic gate violation (e.g. `degree_exceeded`, a direct count against
a fixed target limit) and an unproven heuristic search timeout
(`placement_effort_exhausted`).** `src/tsu/passes/place.py`'s own module and
function docstrings are explicit and correct about the distinction --
*"`_anneal` is a seeded, budgeted heuristic search, not a decision
procedure. When it does not find a legal embedding within its budget, that
is a fact about the search, not about the substrate"* (`place.py:7-9`), and
`geometry_unreachable` (a genuine proof) is *"reserved for a case this pass
can actually PROVE; this pass makes no such proof, so it must never raise
that failure_class here"* (`place.py:216-219`) -- but `search.py:169,229`
maps BOTH outcomes to the identical `CandidateState.HARDWARE_INFEASIBLE`.
**Concrete failure scenario:** today this is latent, not manifest -- the
literal string `"HARDWARE_INFEASIBLE"` has zero display sites in `demo/`
(confirmed by grep; both the Tk app and `tsu report` render only the
recorded `cause`/`reason` prose, which IS honest, e.g. "placement failed:
placement effort exhausted"). But any future consumer of `candidates.json`
or `Candidate.state` directly (a new report renderer, an API response, a
dashboard) that surfaces the bare state name would present a search-budget
timeout with the same word used for a proven hardware violation -- the same
class of latent trap R10's docstring finding describes: correct today only
because nothing currently reads the field literally. **What was checked:**
traced every `HARDWARE_INFEASIBLE`-producing branch in `search.py` (gate
failures at `:169`, the `except CompileError` branch at `:229` which also
catches `degree_exceeded`, `budget_exceeded`, and `parity_conflict` from
`place.py`, none of which are proven-impossible in the same sense as a
magnitude-gate violation except `parity_conflict`, which the code's own
comment calls "should-be-unreachable-in-practice" since mediation
mathematically always succeeds); grepped `demo/*.py` for the literal enum
string (zero hits) and for `_failure_narrative`'s rendering path
(`src/tsu/report.py:394-424`, confirmed it reads only `cause`/`reason`,
never `state`).

### What was tried and did not turn up a finding

- Empty batch (0 draws): `batch_feasibility([])` returns
  `infeasible=False, reason='no draws yet'` -- correctly NOT asserted
  infeasible, matching the function's own docstring ("An empty batch is NOT
  asserted infeasible -- there is no evidence yet either way"). Confirmed
  by direct execution, not just by reading the docstring.
- Partially valid batch (1/10): `infeasible=False` -- confirmed the
  boundary is exactly `valid == 0`, not some fuzzier threshold that could
  misclassify a low-but-nonzero valid rate as infeasible.
- Composite view with a missing layer: `composite_missing_layers` and its
  two call sites (`lattice_app.py:3826-3838` cross-layer readout,
  `:3908-3920` the world-canvas placeholder) both use "unavailable: ...
  has no valid sample yet this session" -- absence-of-evidence framing,
  correctly never claiming impossibility. This is the BEST-worded of all
  six paths and was used as the comparison baseline for the finding above.
- Whether `batch_infeasible` can go stale (keep showing INFEASIBLE after a
  clamp that has since produced a valid draw): traced the reset at
  `:3477-3483` (base) and `:4353-4354`/`:4429-4430`/`:4469-4470` (bands/new
  seed/clamp change) -- every state-changing action that could make a
  previous "infeasible" verdict wrong resets it to `False` before the next
  redraw. No staleness finding.
- Whether the compile-time `HARDWARE_INFEASIBLE` state's REASON text (as
  opposed to its state NAME, covered above) ever says "impossible" for a
  search-budget failure: read every `CompileError` message string raised
  from `place.py` (`"placement failed: degree exceeded"`, `"...node budget
  exceeded"`, `"...placement effort exhausted"`, `"...parity conflict"`) --
  all four name the SPECIFIC mechanism, none say "impossible" or
  "infeasible" in the body text (only the outer, unwrapped `reason` field
  the app never displays raw does). No finding in the rendered text itself.
- `demo/multichunk.py`'s raster-order corner-consistency assertion
  (`:132-138`, `"structurally impossible in raster order"`) is a genuine,
  provable graph-order invariant (two neighbours computing the same
  already-fixed corner cell), not a sampling-absence claim -- checked it is
  not mis-scoped R6 material; it is a code-correctness assertion about
  generation order, unrelated to "zero valid samples."
- CLI/research-script wording (`demo/seam_check.py:273`
  `"C INFEASIBLE -- 0/{n} valid draws"`, `demo/stacked_world.py:120-122,
  164-166` `"no valid world sampled"`) is honest and inline-quantified
  (the draw count sits in the SAME clause, not an aside), but these are
  one-shot CLI scripts (`SystemExit`/`print`, not persistent UI state), so
  they were checked for consistency only, not filed as part of the primary
  finding above, which is about the interactive app's persistent labels.

**Verdict: PASS-WITH-FINDINGS.** No path asserts impossibility as a
permanent, unconditional state -- every "infeasible" verdict is transient
and correctly clears on the next contrary evidence. The finding is narrower
than the brief's worst-case ("proven impossible"): it is that one of two
parallel wordings for the identical event is grammatically weaker than the
other, and the stronger word ("INFEASIBLE") is shared by both.
