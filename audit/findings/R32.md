# R32 -- the sampler spent 99.8% of its time compiling itself

**Status:** MEASURED and FIXED. A performance defect in this project's own
shipped backend, found while trying to run the game.

Reproduce: `pytest tests/test_live_sampler.py`. The class is
`tsu_compiler.backends.live.LiveSampler`.

## What was wrong

`backends.thrml_backend.sample_chains` builds a fresh `IsingSamplingProgram`
and calls `jax.jit` on a **new closure** every call. The closure is a new Python
object each time, so JAX cannot match its compilation cache and re-traces from
scratch on every single call.

Measured on the shipped visibility model, 1536 spins on a 48x32 lattice:

    sample_chains, per call                 183 ms       5.4 fps
    the same work with the trace reused    0.23 ms    4315 fps

A factor of 800.

## How it was found, which is the part worth keeping

Not by profiling. By asking whether the game could run, and then varying the one
knob that should have mattered:

    warmup sweeps per frame     cost per frame
                          60          186 ms
                          30          200 ms
                          10          288 ms
                           4          220 ms
                           2          187 ms
                           1          177 ms

**One Gibbs sweep cost the same as sixty.** A cost that does not move when the
work moves by a factor of sixty is not the work. That table took two minutes and
pointed straight at fixed per-call overhead, where a frame-rate number alone
would have suggested the model was too big and invited the wrong fix -- a
smaller lattice, fewer sweeps, a coarser grid, all of which would have made the
game worse and none of which would have helped.

The physics was never the cost. With the trace reused, sixty-four sweeps per
frame cost 1.10 ms.

## The fix

`LiveSampler` traces once. Two things make that possible.

**Biases are a traced argument, not a closure.** `equinox.filter_jit` treats
array leaves as traced and everything else -- the `SpinNode` objects, the
blocks, the schedule -- as static. So a model whose input is rewritten every
frame reuses one compilation. Closing over the biases instead makes every frame
a new program, which is the original defect.

**The chain carries forward.** A game resumes from the previous frame rather
than re-thermalising from noise. Cheaper, and it is also what makes the picture
stable rather than boiling.

At game scale, biases rewritten every frame, one chain, eight sweeps:

    first frame     311 ms      one compilation
    median frame   0.45 ms      2209 fps
    traces after 41 frames: 1

## The line this draws

Something changes per frame or it does not, and the distinction is not
stylistic:

    STRUCTURE   which spins exist, which are coupled to which, which are
                clamped. Changing any of these is a different program and
                needs a new sampler.
    DATA        the bias on a spin, the value a clamped spin is held at, the
                inverse temperature. These can change every frame for free.

A game moves the player by rewriting biases. That is data, which is the only
reason any of this works. Had the interaction been "clamp the player's cell",
the set of clamped nodes would change as the player moved, that is structure,
and every frame would be a recompilation. The same design decision that R23
forced for correctness -- input as bias, not clamp -- turns out to be the one
that makes it fast. See `programs/visibility_game.py`.

## The trace count is a counted fact, not a hope

A silent retrace gives back the whole 180 ms and is invisible: the draws stay
correct, they just arrive slowly. So `LiveSampler.traces` is incremented inside
the traced function, where it only runs at trace time, and the tests assert
`traces == 1` after twenty-five frames with fresh biases on every one. A
performance property that is not asserted is a performance property that
regresses.

## It is still right

Speed is worth nothing if the answer moved. Decoded visibility against the
exact raycast, single chain, eight sweeps per frame, forty frames of settling:

    input        couplings   agreement with the exact raycast
    clean              ON       97.9%
    clean             OFF       85.4%
    corrupted          ON       60.4%
    corrupted         OFF       10.4%

The ablation is R23's control and it passes decisively: on a corrupted input --
8% spurious walls, the failure a scan cannot recover from -- the couplings take
agreement from 10.4% to 60.4%. They are not inert.

Agreement improves with more FRAMES rather than more sweeps per frame: four
sweeps over four hundred frames reaches 77.1%, while thirty-two sweeps per frame
sits at 68.8% regardless of how long it runs. The persistent chain is still
settling, which is what a persistent chain does, and it is also a reminder that
one configuration read off one chain is a fluctuating quantity. That is R30's
subject, one layer down.

## What this does and does not establish

It establishes that this project's shipped sampling entry point costs roughly
800x what it needs to when driven in a loop, that the cause is re-tracing rather
than sampling, and that a traced-argument sampler fixes it without changing what
comes out.

It does not establish that `sample_chains` is wrong for what it was written
for. One independent run pays one compilation either way, and its uniform-random
restart per call is a feature there. The defect is only a defect under
repetition, which is why nothing caught it until something tried to repeat it.

No hardware claim. Everything above is JAX on CPU through THRML.

## Related

- R23: the retraction that forced input to be a bias rather than a clamp. That
  decision is what makes per-frame updates free here.
- R30: reading one configuration off one chain is a fluctuating quantity. The
  settling table above is the same effect at frame rate.
