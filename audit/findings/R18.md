# R18 -- Performance: classification only (Wave 4)

**Scope discipline:** per the brief, nothing below was optimised, tuned, or
changed. This section classifies where time goes and specifically hunts for
places a speed/cost decision reached into something statistically
consequential -- a sample count, a warmup length, a check that gets skipped.
Two candidates were run down in full and one is a genuine finding; a third,
plausible-looking candidate was checked numerically and **ruled out**,
recorded here because a review that only reports confirmed compromises,
without showing what was checked and cleared, is not distinguishable from
one that did not look.

## Cost classification (figures read live, from this receipt's own files)

**One-time, at compile ("receipt-build"), never re-paid live**
(`demo/receipts/small/passes.json`'s own `pass_durations`, quoted verbatim):

| stage | wall time | note |
|---|---:|---|
| `place` | 201.351 s | dominant cost; the WINNING (`domain_wall`) candidate's own placement search alone -- confirmed by reading `_compile_spec_impl` (`src/tsu_compiler/passes/search.py:368-435`): `durations = dict(art.get("durations", {}))` at `:433` is `arts[chosen.encoding][1]`'s own dict, never summed across the rejected `one_hot` candidate's separate, also-costly placement attempt (which failed with `placement_effort_exhausted` after its own full 12-restart/200000-iteration budget, per `passes.json`'s `candidates[1].failure`) -- so the displayed 201s genuinely belongs to the encoding actually shipped, not inflated by the rejected alternative's cost. |
| `verify` | 2.931 s | includes the sampler call below plus task/execution/cross-check layers |
| `encode`/`lower`/`analyse`/`gate_checks`/`route`/`build_program`/`regime` | 2.9ms-5.7us combined | negligible next to `place` |

Within `verify`, `demo/receipts/small/cost.json`: the `sample_chains` call
itself (`n_chains=32, n_samples=200, n_warmup=400, steps_per_sample=2`) took
**0.944 s** (6783 samples/s) to draw 6400 total samples.

**Live, re-paid every draw/batch while the app runs** (module-level
constants, `demo/lattice_app.py:112-138`, cross-checked against A1's live
trace, not merely read): unclamped tick, `n_chains<=6` (speed-scaled),
`n_warmup=300` fixed, ~0.2-0.3s/tick per the module's own measured-timing
comment (`:113-116`); clamped batch, `n_chains=6` fixed, `n_warmup=600`
fixed, `n_samples` 3-30 (speed-scaled), ~0.4s steady-state after a one-time
~1.4-1.7s JIT compile per distinct `(n_chains, n_samples)` shape (`:206-
209`'s own measured-timing comment, task cited: `ui2-report.md`) -- the JIT
cost is why `SPEED_LEVELS` uses four fixed, discrete tiers (`:219-228`)
rather than a continuous slider: a continuous `n_chains`/`n_samples` control
would multiply the number of distinct JIT-compiled shapes a session might
hit, each paying its own first-use compile tax. This is a real
speed-vs-cost design choice, but it constrains **batch size/cadence only**
(`n_chains`, `n_samples`) -- R12 already independently verified those two
parameters cannot reach the distribution -- so it is noted here as
classification, not filed as a finding.

**Display-only, throttled, and correctly scoped to not skip any
computation on the underlying data:** `SCOPE_REDRAW_EVERY_N_DRAWS=5`
(`:255-258`, `:3518-3527`) skips *redrawing* the SCOPE panel's five
sub-plots on 4 out of every 5 draws -- confirmed by reading `_handle_msg`
that `energy_trace`/`magnetization_trace`/`raw_draws`/`valid_frac_trace`
are all appended to **unconditionally**, before the throttle check
(`:3458-3514` happen before `:3524-3527`'s gate) -- so a throttled redraw,
when it does fire, reflects the full accumulated history since the last
one, never a gap in the underlying data. The module comment's own framing
-- "plenty for a display, not a measurement" (`:3521-3523`) -- is the
correct distinction this whole review section is built to check, and it
holds here.

## Findings

### Moderate

**The one live parameter that determines the sampled distribution itself
(`N_WARMUP`, and to a lesser extent `CLAMP_N_WARMUP`) is sized by a
UI-responsiveness budget, not by any convergence diagnostic run against the
receipt it is used on.** `demo/lattice_app.py:112-116`'s own comment for
`N_WARMUP=300`: *"Chosen from a measured timing check: a single (n_chains=6,
n_samples=1, n_warmup=300) call on this 192-node program takes ~0.2-0.3s...
so a batch comfortably lands inside one UI tick."* `CLAMP_N_WARMUP=600`'s
own comment (`:129-135`) is explicit that its size is an affordability
judgement, not a derived sufficiency bound: *"Bigger than the unclamped
per-tick batch... because a pin change is a deliberate, infrequent gesture
-- the app **can afford** one solid batch's worth of draws to answer... **
honestly**"* -- language that, by implication, treats the smaller,
per-tick-constrained 300 as the less-affordable, less-rigorously-justified
choice of the two, even though nothing downstream ever flags unclamped
draws as less trustworthy than clamped ones for that reason. **Concrete
failure scenario:** neither live constant is validated against this
receipt's own measured mixing time anywhere the app runs -- the only
mixing-time-aware figure in the whole system is the compile-time,
frozen `verification.json`'s `ess: "unavailable... tau~=5.58"`, computed
under `n_warmup=400` (`_VERIFY_SAMPLE_PARAMS`, a *third*, still-different
warmup value from both live constants), which the live SCOPE panel does
not read (A2's own M-2 finding) and which itself carries no burn-in
adequacy claim, only a mixing-*time* one. On the numbers actually measured
for this receipt (tau~5.58), 300 steps is generous (~54x tau) and very
likely adequate -- so this is not, on the evidence available, currently
producing a wrong answer -- but the app's own code never says why 300 is
enough beyond "fits in a UI tick," and if a future receipt swapped into
`RECEIPT_DIR` (`:61`, currently hardcoded to `demo/receipts/small`) mixed
an order of magnitude more slowly, nothing in this app would notice: there
is no live burn-in check, and the timing-derived constant would not
automatically grow to compensate. **What was checked:** every
`n_warmup=`/`N_WARMUP`/`CLAMP_N_WARMUP` assignment and its surrounding
comment (`:112-138`, `:159`, `:1403-1404`, `:1430-1431`); confirmed (per
R12's own analysis) these are genuinely fixed, receipt-agnostic module
constants, not derived per-session; computed the ratio against this
receipt's own frozen `tau~=5.58` (300/5.58 ~ 54, 600/5.58 ~ 108) to confirm
this is not currently manifesting as a wrong answer, only as an
undocumented, untested assumption. **Not performed (Phase F candidate):** a
live or compile-time cross-check that the app's own `N_WARMUP`/
`CLAMP_N_WARMUP` are some minimum multiple of the receipt's own measured
`tau` (when available), surfaced as a gate rather than left implicit.

### Checked and ruled out (recorded per this task's "what was tried" requirement)

**Hypothesis: `_VERIFY_SAMPLE_PARAMS` (`n_chains=32, n_samples=200`,
`src/tsu_compiler/passes/search.py:513-514`) was sized small for compile-time cost,
and that is why this receipt's frozen `ess` reads `unavailable` (`N/tau=
1147 < 5000`).** Checked numerically, not assumed: `_verify` is called
**exactly once** per compile, on the single already-chosen candidate
(`_compile_spec_impl:432-433`) -- never inside the placement search's own
retry loop -- so its cost is not multiplied by placement restarts. Its
measured cost (`cost.json`: 0.944s for 6400 samples, 6783 samples/s) is
**~213x cheaper** than the `place` stage's 201.351s that already dominates
this same compile. Clearing `RELIABILITY_MIN_N_OVER_TAU=5000` at this
receipt's own `tau~=5.58` needs `N >= 27900` (vs. the current 6400) --
roughly 4.4x more samples, i.e. **~4.2s** more sampler wall time added to a
compile that already costs ~204s total. **This is not a cost-constrained
choice on the evidence available: the budget to make this specific
receipt's `ess` reliable was affordable and was not spent.** This is
recorded here, not as an R18 "cost forced a compromise" finding (cost did
not force it -- the numbers show it was cheap and available), but as the
negative result the brief's "what was tried and did not turn up a finding"
requirement asks for: a plausible-looking cost story that a live check
against the actual timings does not support. Whether `n_samples=200` is a
receipt-agnostic default nobody has revisited (a design-quality question,
not a performance one) is out of this section's scope.

### What was tried and did not turn up a finding

- Checked whether `DETACH_REFRESH_MS=250` (`:285-287`, a detached window's
  own independent redraw cadence) causes any statistic to be recomputed
  from a smaller/staler sample than the inline SCOPE panel uses -- both read
  the identical `self.` state at redraw time (`_render_detached_plot`,
  `:4219-4247`); the only difference is *how often* the identical
  computation reruns, never *what* it runs over. No finding.
- Checked whether `MAXCUT_EXACT_LIMIT=20` (`src/tsu_compiler/passes/analyse.py:17`)
  or `EXACT_LIMIT=18` (`src/tsu_compiler/backends/thrml_backend.py:35`) -- both
  exact-computation cost ceilings -- are ever silently approximated past
  their limit rather than honestly marked unavailable. Traced
  `rep.mediators`'s `-1` sentinel (mediator lower bound, cost-limited past
  `MAXCUT_EXACT_LIMIT`) through to `receipt.py:219-233`, which converts it
  to `null` plus an explicit `"not computed: graph exceeds..."` note before
  it ever reaches `metrics.json` -- correctly disclosed, not a compromise
  laundered as a measurement. No finding (this is the correctness-cost
  boundary working as designed, cited here as the classification the brief
  asks for, not as a defect).
- Checked whether the SCOPE panel's redraw throttle (`SCOPE_REDRAW_EVERY_
  N_DRAWS=5`) could cause the ACF/tau plot specifically to read a
  smaller/older `energy_trace` slice than what has actually accumulated --
  confirmed (see above) the underlying trace append is unconditional and
  independent of the redraw gate; when `render_acf_plot` does run, it
  always sees the full, current `energy_trace.ys`. No finding (independent
  of, and does not change, R4/A2's already-filed C-1 finding about what
  that series itself validly supports).
