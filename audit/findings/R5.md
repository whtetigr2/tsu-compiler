# R5 -- Codeword / contract / conditioning (Wave 4)

**Method:** enumerate every place the live app makes a conditioning claim
(`p(x | valid)` prose, a per-layer "valid" label, the composite validation
readout, the PINS panel, a pin-honouring guarantee), then read the exact
code computing the number or gating the claim, cross-checked against
`src/tsu_compiler/spec.py`'s own `TaskContract.validate` and the receipt/spec files on
disk (`demo/receipts/*/spec.yaml`) rather than trusting a label's wording.
The brief's own "known instance" (an overlay contract with zero rules) is
verified first, independently, then used as the template for hunting
further mismatches between conditioning APPLIED and conditioning CLAIMED.

## The known instance, independently re-verified: `elev_band`'s zero-rule contract

Confirmed from three independent sources, not one:

1. **The spec file itself:** `demo/receipts/elev_band/spec.yaml` (43 lines,
   read in full) contains no `contract:` key anywhere -- `grep -n contract`
   on the file returns zero matches.
2. **The loader:** `src/tsu_compiler/spec.py:444`, `rules = tuple(raw.get("contract",
   {}).get("validate", []) or ())` -- an absent `contract:` key yields
   `rules = ()`.
3. **The validator:** `TaskContract.validate` (`src/tsu_compiler/spec.py:38-64`)
   loops `for r in self.rules: ...`; with `self.rules == ()` the loop body
   never executes, `out` stays `[]`, and `ValidationResult(ok=not out, ...)`
   is `ok=True` for every assignment handed to it -- vacuously, not because
   anything was checked.

**This is not a live finding: it is already disclosed, correctly, on
screen.** `demo/lattice_app.py:3881-3904` (`_refresh_layer_view`'s band
branch) measures `n_rules = len(self.overlay_receipt.spec.contract.rules)`
**live**, not from a hardcoded assumption, and when `n_rules == 0` renders:

> `"this overlay's contract declares 0 rules, so \"valid\" means only
> \"decoded as a codeword\" -- the contract-pass check is vacuously true for
> every codeword, not evidence any rule was satisfied"`

right next to the band's own `valid {count}/{total}` line -- the exact
juxtaposition the brief warns about (a vacuous 100%-capable rate shown
beside base's genuinely rule-checked one) is defused by naming the
mechanism, in the same sentence, every time a band is viewed. The code's own
comment (`I1 (fix-round-2)`) says this was a prior finding already
corrected here; independently re-run and re-read, that correction holds --
`n_rules` is computed from the live `TaskContract` object every call, not
cached or asserted, so it cannot drift out of sync with the spec file.
**Verdict: PASS (verified, not merely inherited).**

**Verdict: PASS (verified, not merely inherited).**

## Findings

### Minor

**The overlay-pin docstring asserts a magnitude ("rarely") for how often a
pinned band cell disobeys its pin, but nothing measures or displays that
rate -- unlike the sibling cross-layer claim, which does.**
`overlay_pin_patch`'s docstring (`demo/lattice_app.py:857-868`): *"a pinned
overlay cell can still, **rarely**, sample the other way"* -- this word does
not reach the screen (the on-screen disclosure at `:2609-2613` correctly
says only that the pin "can still render the other value," with no
frequency claim), so no viewer is misled by it directly. But contrast this
with `monotonicity_violations` (`demo/elevation.py:50-68`), which exists
specifically because "a later task is required to measure" cross-layer rule
breakage rather than assume its rate (`demo/elevation.py:20-28`), and whose
measured rate is displayed live every time the composite view is opened
(`_refresh_composite_readout`, `demo/lattice_app.py:3839-3848`). No
equivalent measurement exists for how often an `OVERLAY_PIN_STRENGTH=3.5`
pin is actually honoured by a regenerated band, even though the data to
compute it is already in hand: `_on_band_regenerated`
(`demo/lattice_app.py:4339-4372`) receives `msg["valid"]`, the full list of
this batch's decoded, contract-valid draws, and could trivially compute
`sum(1 for d in valid if d[cell] == pinned_value) / len(valid)` per pinned
cell the same way `batch_feasibility` already summarises `valid`/`total` for
the status line. **Concrete failure scenario:** a developer reading
`overlay_pin_patch`'s docstring (the only place "rarely" appears) takes the
word at face value when deciding whether a future feature can treat an
overlay pin as "basically reliable" -- the project's own epistemic-discipline
rule (`Empirical Re-Verification`) is exactly what this word skips: a
magnitude claim with no measurement backing it, sitting in the same
docstring that otherwise prides itself on `FieldCapExceeded` being "reported
... instead of laundered through" (`layers.py:110-114`). **What was
checked:** grepped `demo/*.py` for any pin-honour-rate computation (none
found) and for every on-screen string mentioning overlay pins (`:2609-2613`,
`:3900-3904`) -- neither repeats "rarely" or any other frequency word, so
this is a source-comment-only claim, not a screen-facing one, which is why
it is filed Minor rather than Important. **Not performed (Phase F
candidate):** compute and report an empirical honour rate per regenerate,
the same way monotonicity is already reported, or soften the docstring's
"rarely" to "not always" (a claim the code already substantiates: `strength`
is bounded by `FIELD_CAP` combined with `band_patch`'s own terms, so an
overlay pin can genuinely be outvoted, per `:2611-2612`'s own on-screen
text) without asserting a frequency nobody measured.

### What was tried and did not turn up a finding

- **VERIFICATION panel's `task_validity`:** re-derived from `search.py:588-
  596` that it is `P(codeword AND contract-valid)` over **every** raw draw
  (the denominator is `len(got)`, all 6400 draws, not just codewords) --
  matches `demo/explainer.py:255-272`'s "roughly three quarters of raw draws
  are discarded" framing and A2's own independent re-measurement
  (`task_validity=0.24703125` frozen vs. `5/18=27.8%` live, both consistent).
  No conflation found between this MARGINAL probability and the DECODED
  WORLD panel's conditional `p(x | valid)` framing -- the two are computed
  by different code, for different purposes, and neither claims to be the
  other.
- **Live `valid fraction` label's conditioning:** re-confirmed (independent
  of A2's own re-count) that `self.total_draws`/`valid_count`/
  `contract_fail_count`/`noncodeword_count` are updated in exactly one place
  (`_handle_msg`, `:3449-3511`) and that the three named buckets partition
  the total by construction -- no fourth silent bucket, no double-count.
- **Clamp honouring (base):** re-checked (independent of A1/A2's own trace
  read) that `_run_clamped_batch` (`:1426-1454`) passes `clamp=self.clamp`
  straight into `tsu.simulate.simulate`, never post-filtering or relabelling
  a draw that violates the pin -- `state_clamp` (thrml's own mechanism)
  fixes the physical spins before sampling, so a "valid" clamped draw's pin
  cell cannot read anything but the pinned value by construction, not by a
  downstream check that could silently pass a violation.
- **Composite "valid" semantics:** `composite_missing_layers`
  (`:874-882`) gates the composite view behind every layer having at least
  one valid decode -- confirmed it never fabricates a partial composite, and
  its "unavailable: ... has no valid sample yet" wording (used at both call
  sites, `:3831-3837` and `:3910-3920`) is absence-of-evidence framing, the
  same convention R6's wave already verified for the base layer's zero-valid
  paths. Consistent, not re-litigated.
- **PINS panel wording for base vs. overlay pins combined in one list:**
  `_refresh_pins_panel` (`:3640-3654`) prints `"base: name = value"` and
  `"band0: name = value"` lines together under one "PINS" header with
  identical formatting -- checked whether this format itself implies the two
  are the same kind of thing. It does not overclaim, because the LAYERS
  panel's own disclosure label (`:2608-2616`, verified above) sits
  immediately above/beside this same list in the running layout and states
  the distinction in the one place a viewer would look to understand what a
  "pin" line means here.
