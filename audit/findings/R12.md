# R12 -- UI must not change the mathematics (Wave 4)

**Method:** the brief's own instruction is "verify the code, not the
comments," so every claim below was checked by reading the actual data flow
(never a docstring's assertion alone), then corroborated against A1's live
trace where the trace already covers the same call sites. Checked, in order:
the speed control's structural inability to reach `n_warmup`/
`steps_per_sample`; every other interaction the brief names by name (pause,
resize, detach, layer switch); and one the brief does not name explicitly
but which genuinely changes sampling parameters -- the per-layer temperature
control -- to determine whether it is a "display path" in the sense this
review must police, or a disclosed, explicit user action outside that scope.

## The speed control: structurally, not just observationally, incapable of touching `n_warmup`/`steps_per_sample`

**Static proof, not a sampled test of a few speed levels:**
`SPEED_LEVELS` (`demo/lattice_app.py:219-228`) is a tuple of four dict
literals, each with exactly the keys `{"label", "chains", "clamp_samples",
"delay_s"}` -- `n_warmup`/`steps_per_sample` are not among them, in any of
the four entries, so there is no level index at which they could be present.
`speed_level(idx)` (`:290-297`) does nothing but clamp `idx` into range and
index into this tuple -- it manufactures no new keys. Its own docstring
states the structural guarantee explicitly: *"Every entry's keys are exactly
{...}: no entry can smuggle in an n_warmup or steps_per_sample override,
which is the structural guarantee that this control cannot touch the
statistics."* Read the dict literals directly (not the docstring's claim
about them) to confirm this -- it is correct.

**Every real assignment site for `n_warmup`/`steps_per_sample`, found by
grep across the whole file, is one of exactly four lines, and every one
reads from a bare module-level constant:**

```
demo/lattice_app.py:159   n_warmup=CLAMP_N_WARMUP, steps_per_sample=STEPS_PER_SAMPLE   (BAND_SAMPLE_PARAMS)
demo/lattice_app.py:1410  n_warmup=N_WARMUP,       (unclamped tick -> thrml_sample)
demo/lattice_app.py:1411  steps_per_sample=STEPS_PER_SAMPLE,
demo/lattice_app.py:1438  n_warmup=CLAMP_N_WARMUP, (clamped batch -> simulate)
demo/lattice_app.py:1439  steps_per_sample=STEPS_PER_SAMPLE,
```

`N_WARMUP=300`, `CLAMP_N_WARMUP=600`, `STEPS_PER_SAMPLE=4` are plain
module-level integer constants (`:119-120,138`), never read through
`speed_level(...)` or any per-call computation -- there is no code path from
`self.speed_idx`/`SPEED_LEVELS` to either name. `SampleWorker`'s own class
docstring (`:1300-1309`) makes the same claim; the grep above verifies it
from the assignment sites themselves, not from the docstring repeating it.

**`SampleWorker.set_speed`** (`:1337-1341`) does exactly one thing: `self.
speed_idx = idx`. No other attribute is touched, and `speed_idx` is read in
exactly two places downstream: `speed_level(self.speed_idx)["chains"]`
(`:1402`, unclamped) and `speed_level(self.speed_idx)["clamp_samples"]`
(`:1429`, clamped) -- both already shown above to be incapable of yielding
`n_warmup`/`steps_per_sample`.

**A1's own live trace corroborates this dynamically, not just statically:**
at `speed_idx=0` (the slowest, most different-from-Full level), the traced
unclamped call still carried `n_warmup=300` and the traced clamped call
still carried `n_warmup=600` -- the exact same constants used at every other
speed level (`truth_table.md`'s `sample` row; independently re-confirmed
here by re-reading `audit/traces/unclamped_trace.json` /
`clamped_trace.json` directly rather than re-quoting A1's own summary).

**Live UI-facing disclosure of this same guarantee, checked as a screen
string, not only as an internal comment:** `_refresh_speed_label`
(`:4389-4395`) renders `f"... -- display rate only, n_warmup/steps_per_sample
unchanged)"` every time the slider moves -- the claim under test in this
section is stated, verbatim, on screen, and the analysis above confirms it
is true.

**Verdict: the speed control provably leaves the sampled distribution
untouched, at every level, in both draw modes.** Not merely "the tests
pass" or "the docstring says so" -- the four assignment sites are
exhaustive (found by grep across the entire file, not by reading only the
functions the brief pointed at), and this exhaustiveness, not a test result,
is what the verdict rests on. The test suite separately guards
`SPEED_LEVELS`'s own shape (verified below to be a real, correctly-written
guard) but has no test on the CALLER side of this same guarantee -- see
Minor finding below for exactly what that gap does and does not cover.

## Batch truncation on Pause does not truncate sampling, only display

A second way the speed/pause controls could have leaked into the
mathematics: if clicking Pause mid-batch caused fewer samples to be *drawn*.
Checked directly: in `_run_clamped_batch` (`:1426-1454`), `simulate(...,
n_samples=n_samples, ...)` (`:1435-1440`) runs to completion -- the full
`n_chains x n_samples` draw is computed by `thrml`/`simulate` before the
method ever inspects `pause`/`stop_evt` -- and only the **subsequent
row-by-row push loop** (`:1446-1450`) checks `should_abort_batch`
(`:1258-1276`) before each row is enqueued to the UI. `should_abort_batch`'s
own docstring is explicit about the scope of what it stops: *"stop pushing
further rows from the batch that is ALREADY computed and in hand"*
(`:1259-1261`). So a Pause click can shorten what reaches the SCOPE
panel/log/valid-fraction counters for that one in-flight batch, but never
shortens the sampler call itself -- confirmed by reading the call order
(`simulate()` fully returns at `:1440` before the loop at `:1446` begins),
not merely inferred from the docstring. This also means the identical
`should_abort_batch` mechanism cannot be a route by which Pause biases which
subset of an i.i.d. batch gets counted in a state-dependent way: the break
point is determined by wall-clock timing of the pause click relative to the
push loop, not by anything about the rows' own values.

## The other named interactions: pause, resize, detach, layer switch

- **Pause** (`_toggle_pause`, `:4036-4043`): sets/clears
  `self.worker.pause` (a `threading.Event`). `SampleWorker.run` (`:1369-
  1379`) reads it only to decide whether to call `_run_one_batch` at all --
  it never alters what that call, when it does run, passes to the sampler.
- **Resize:** grepped every `bind("<Configure>", ...)` site in the file
  (`:2298,2299,2814,4184`) -- the main window's own scroll-region handlers
  (`:2298-2299`) and the footer's line-wrap handler (`:2814`) only
  reflow/redraw Tk widgets; none reach `self.worker`, `self.clamp`, or any
  sampler call. The fourth (`:4184`) is the detached-window caption
  re-wrap handler, covered next.
- **Detach:** `_open_detach`'s redraw loop (`:4140-4147`, ticking on its own
  `DETACH_REFRESH_MS=250` timer) and `_render_detached_plot`
  (`:4219-4247`) both **only re-render already-held state** -- `self.
  energy_trace`, `self.raw_draws`, `self.receipt.im`, etc. -- through the
  identical `render_*` functions the inline SCOPE panel already calls
  (confirmed by reading the dispatch table directly: every branch reads an
  existing `self.` attribute, none calls `thrml_sample`/`simulate`/any
  worker method). Opening, resizing, or closing a detached window changes
  only what is drawn from data already collected, never the collection
  itself.
- **Layer switch** (`_on_layer_selected`, `:3699-3707`): reassigns
  `self.active_layer` and calls four `_refresh_*` methods -- all confirmed
  to be pure redraws of already-held per-layer state (`LayerState`
  attributes, `self.last_valid_grid`), never a sampler call. Selecting a
  band does not itself sample that band; sampling only happens on an
  explicit "Regenerate this layer" click (`_on_regenerate_click`, wired to
  `_regenerate_band_async`, `:4266-4268`).

## The temperature control: a real parameter change, correctly scoped outside this review's target

`_on_temp_canvas_interact` (`:3715-3741`) calls `set_beta_override`
(`:390-399`), which does nothing but store a float on `LayerState.
beta_override` or `self.base_beta_override` -- confirmed by reading both
functions in full: **neither samples anything**. The stored value is read
exactly once downstream, at the *start* of the *next* explicit "Regenerate"
click (`_regenerate_band_async:4304`, `beta_override = layer.
beta_override`, read before `work()`'s closure captures it) -- dragging the
slider mid-session changes a stored preference, not the distribution any
already-displayed world was drawn from, and the docstring's "Moving this
re-samples ... on its NEXT regenerate; it does not recompile" claim
(`:3816-3817`) is what actually executes. This is **not** a violation of
"UI must not change the mathematics": temperature IS mathematically
consequential by design (spec 5.3.5's beta gate), and this control is not a
display-rate knob mislabelled as one -- it is a disclosed, explicit,
one-way action (the ADJUSTABLE/FIXED seal framing, `:3781-3818`) applied
only to unmediated (bipartite) overlay bands, gated on the same
`assert_beta_consistent`-keyed fact the base layer's own beta lock uses.
Distinguishing this from the speed control's "display only" claim, which
this review must hold to a stricter standard, is itself the correct
adjudication here, not an oversight.

## Findings

### Minor

**The test suite guards `SPEED_LEVELS`'s own shape (correctly, and more
strongly than first assumed -- see below) but has no test asserting the
CALLER'S actual behaviour: that `_run_unclamped_tick`/`_run_clamped_batch`
pass the bare `N_WARMUP`/`CLAMP_N_WARMUP` constants to the sampler
regardless of `speed_idx`.** Checked `tests/test_lattice_app_logic.py`
directly (not assumed absent): `test_speed_levels_nonempty_and_well_formed`
(`:292-299`) DOES assert `set(lvl.keys()) == {"label", "chains",
"clamp_samples", "delay_s"}` for every entry, and
`test_speed_levels_never_names_warmup_or_steps` (`:302-307`) DOES assert
`"n_warmup" not in lvl` -- so the specific scenario of a future
`SPEED_LEVELS` entry silently growing an `n_warmup` key is already
guarded, correctly, and reasonably strongly. **What neither test reaches:**
both inspect only the static `SPEED_LEVELS` tuple itself; neither
constructs a `SampleWorker`, calls `_run_unclamped_tick`/
`_run_clamped_batch`, or inspects a `sampler_params` dict. A regression that
left `SPEED_LEVELS` completely untouched but made `_run_unclamped_tick`
derive its `n_warmup` from `speed_level(self.speed_idx)["chains"]` via new
in-function arithmetic (rather than reading the bare `N_WARMUP` constant)
would leave every existing speed-related assertion passing. **Concrete
failure scenario, and independent test-potency verification:** worked
through this exact scenario, and the exact assertions it would and would
not trip, in `R19.md`'s "test-potency exercise" (assertion 1) -- filed there
rather than duplicated here in full, since it is as much a finding about
test coverage (R19's mandate) as about the speed control itself (this
section's). **What was checked:** re-read both `SPEED_LEVELS` tests in
full to confirm what they actually assert (correcting an earlier, looser
reading of this session's own notes); grepped `tests/test_lattice_app_logic.
py` for `n_warmup` and confirmed its only three occurrences are inside
`test_speed_levels_never_names_warmup_or_steps`'s own body/comment -- no
test anywhere asserts the VALUE `_run_unclamped_tick`/`_run_clamped_batch`
actually pass. **Not performed (Phase F candidate):** a test that
constructs a `SampleWorker` (or calls `_run_unclamped_tick` directly against
a stub queue) at two different `speed_idx` values and asserts the pushed
`sampler_params["n_warmup"]` is identical across both.

### What was tried and did not turn up a finding

- Attempted to trace a path from `self.speed_idx` to any sampler-affecting
  parameter other than `n_chains`/`n_samples`/`clamp_samples` -- none
  exists; every `speed_level(...)[...]` access in the file was enumerated
  by grep and each indexes only `"chains"`, `"clamp_samples"`, or
  `"delay_s"`.
- Checked whether `_pace_delay`'s inter-batch sleep (`:1387-1398`) could
  affect anything sampled -- confirmed it runs strictly *between* batches,
  after a batch's own draws are already pushed (`:1394`'s own comment: "it
  cannot alter what gets sampled"), and it only ever calls `time.sleep` in
  short slices -- no sampler call inside it.
- Checked whether `_new_seed`/`_restart_sampling_for_clamp_change`
  (`:4415-4492`), both triggered by explicit user gestures (New Seed
  button, pin change) rather than passive UI events, could be reachable
  from a passive interaction (resize, detach, pause) -- traced every call
  site of both (`grep -n "_new_seed()\|_restart_sampling_for_clamp_change()"`)
  and confirmed each is wired only to an explicit button/pin-click handler,
  never a `<Configure>`/detach/pause code path.
- Checked whether opening a detached window's `<Configure>`-driven caption
  re-wrap (`_on_configure`/`_apply_configure`, `:4179-4184`) could, via its
  debounce timer, race with or otherwise perturb the worker thread -- it
  only touches the caption `Label`'s own `wraplength`/height on the Tk main
  thread; no cross-thread state shared with `SampleWorker` is touched.
