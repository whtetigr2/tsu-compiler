# R26 -- the oracle test does not test what ships

**Status:** FOUND, open. Not a retraction. Nothing false was published, but a
test that was relied on as a regression guard covers a different compile from
the artifact it is guarding.

Found by looking at the rendered interface, not by reading code. The example
picker shows a workload's spin count beside its name and a written description
of its hardware cost underneath. For `prog_seq_design_longer` those read **32**
and **16**.

## Both numbers were right, about different things

    prog_codon_opt_tiny       receipt: domain_wall   18 spins   6 mediators
    prog_ecology_lotka_lite   receipt: domain_wall   16 spins   0 mediators
    prog_seq_design_longer    receipt: one_hot       32 spins   8 mediators

A fresh preflight of the same three specs reports 12, 16 and 16 logical spins,
all domain-wall. The eight-position workload is the one where the two diverge,
because its receipt is the only one that is not domain-wall.

## Why

`preflight.model.load_model` hardcodes the encoding:

    if spec is not None:
        return lower(encode(load_spec(str(spec)), "domain_wall").model)

Its own docstring says it "runs the same `encode` -> `lower` the rest of the
toolchain uses, so preflight reports on the model that would actually be
compiled rather than on a parallel reconstruction of it." That is true of the
lowering and false of the encoding.

`passes.search.compile_spec` does not hardcode anything. It searches
`SLICE_ENCODINGS = ("domain_wall", "one_hot")`, keeps every candidate including
rejected ones as evidence, and selects among the feasible ones by physical p-bit
count. For `seq_design_longer` it selected one-hot, which is the larger model at
24 logical spins against domain-wall's 16. Selection ordering by p-bit count
among FEASIBLE candidates means domain-wall was not feasible at the budget that
produced the receipt, even though a fresh preflight places it at 24 restarts and
250,000 iterations.

## What this costs

`backend/tests/test_extropic_oracle.py` is the project's strongest regression
signal, on the stated grounds that nobody here chose the shape of Extropic's
workloads. It calls `preflight(load_model(spec=...))`. So it proves each spec
compiles **under domain-wall encoding**. It does not exercise the encoding
search, and it does not compile the model the shelf actually ships.

A change that broke one-hot encoding, or broke encoding selection, would leave
that test green.

The same gap reaches the Observatory's self-test, which compiles
`ecology_lotka_lite` through `program_service` on every build. That path uses
`compile_program`, not `load_model`, so it is closer to the real thing, but the
workload it checks is the one where the two agree.

## What was done now

Only the visible contradiction. `verified_workloads.py` gained
`receipt_encoding`, `receipt_spins` and `receipt_mediators`, checked against the
receipt on disk by a test, and the written descriptions were rewritten to
describe the shipped receipt rather than a fresh domain-wall preflight. The
eight-position workload's description now names the encoding explicitly and says
both numbers, because the honest statement is that the count depends on which
model you are looking at.

That stops the interface contradicting itself. It does not close the gap.

## What would close it

Parametrize the oracle test over encodings, or over the encoding the receipt
records, so it compiles what ships. The cheap version is to add a second
parameter axis from `SLICE_ENCODINGS`; the faithful version is to call
`compile_spec` and assert on the selected candidate, which also puts the
selection logic under test for the first time.

Not attempted here. Scoped, and it belongs with the compiler rather than with
the interface work that surfaced it.

## The general lesson, which is this project's usual one

The defect was invisible in the code and in the test suite, and obvious on
screen the moment two numbers describing the same object sat next to each other.
`CLAUDE.md` already says to look at the artifact. This is the fourth time that
has been the thing that found it.
