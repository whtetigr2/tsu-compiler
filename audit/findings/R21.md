# R21 -- an assertion that did not check what its own message claimed

**Status:** FOUND and FIXED. Small, but the same shape as R20 and found the same
way -- by asking of each claim whether the evidence under it actually says that.

**Method:** the claims-vs-evidence audit, continued into the two remaining
claim-bearing documents in Claude's tree: `docs/EXTROPIC-NOTE.md` and
`audit/THERMALIZERS_SHAPED_COMPLETE.md`.

## The defect

`audit/THERMALIZERS_SHAPED_COMPLETE.md` scores rubric row A3 as **PASS**:

> Every field falls back to `unavailable` with a reason. An unmeasurable error
> bar prints why, never `0.000`.

The guard behind that is `tests/test_verify.py::test_verification_says_unavailable_rather_than_guessing`,
which compiles a model too large to enumerate and asserts:

```python
assert isinstance(d[field], str) and d[field].startswith("unavailable"), \
    f"{field} must read 'unavailable: <reason>', not a fabricated number " \
    f"or a bare 'unavailable' with no reason -- got {d[field]!r}"
```

The failure message promises to reject *"a bare `'unavailable'` with no reason"*.
The assertion does not do that, because:

```
>>> "unavailable".startswith("unavailable")
True
```

The bare literal passes the check that its own message says would catch it. A
regression emitting `"unavailable"` with no reason attached would have gone
through silently while the test reported success.

## Why this mattered more than its size suggests

The `unavailable`-with-a-reason contract is not incidental -- it is the property
the project leads with. `verify.py`'s module docstring opens with *"Never
fabricates: absent a reference, the field reads 'unavailable' with a reason"*,
and rubric row A3 cites it as evidence of exactly that discipline. The one test
standing behind it enforced the word and not the reason.

## The fix

An explicit second assertion, placed directly beneath the first:

```python
assert d[field].startswith("unavailable:") and d[field][12:].strip(), (
    f"{field} is a bare 'unavailable' with no reason attached -- "
    f"saying WHY is the entire point of the field -- got {d[field]!r}")
```

**Mutation-verified.** Rewriting every `"unavailable: <reason>"` string in
`src/tsu_compiler/passes/search.py` to the bare literal (9 occurrences) now
FAILS the test at the new assertion. Under the old assertion alone that mutation
passed. `src/` reverted clean afterwards -- `git diff --stat` empty.

## What was checked and found sound

Not every hypothesis in this pass produced a defect, and the negatives are
recorded so the same ground is not re-turned:

- **A3's underlying behaviour is correct.** Hand-constructing a `Verification`
  without running `_verify` does produce a bare `task_validity` and an unpaired
  `diversity_valid_samples`. That looked like a defect and is not: `verify.py`
  documents those defaults as deliberate backward compatibility for "an older
  caller, or a test", and a real compile sets them. Confirmed against a genuine
  receipt, `out/toy-z1/verification.json` -- every field populated, and the one
  `unavailable` field (`cross_check_tv`) carrying a full reason.
- **Wolfram cross-check** (`audit/oracles/wolfram.py`, cited in R9/R10) exists.
- **Pre-registered chi-squared** work exists (`audit/r15_oracle_comparison_check.py`,
  R15).

## A second correction, in `docs/EXTROPIC-NOTE.md`

Under the heading "What is already proven", the note stated flatly:

> Mediator marginals ~1e-16.

The measurement is real and is machine precision. Its **scope was not stated**.
The marginal-preservation property is verified against a brute-force oracle on a
3-spin frustrated triangle and a 5-spin odd cycle -- those are the largest cases
in `tests/test_mediator_insertion.py`, because the oracle enumerates `2**n`. The
full spike model inserts **1,878 mediator gadgets**.

The algebraic argument should hold at any size, but "proven" without a range
invites the reader to assume it was measured at the size we actually ship. The
sentence now names the models it was measured on, says plainly that full-spike
verification is **not yet done**, and points at Check 4 of
`audit/GROK_VERIFICATION_DISPATCH.md`, where it is scoped.

The stale test count in the same heading (872) was refreshed to 900.

## The pattern, now three for three

R20 was a correct measurement wrapped in a sentence the data did not support.
R21 is an assertion whose failure message overstated what it verified, and a
proven result quoted without its range. Different artifacts, identical failure:
**the numbers were right every time, and the sentence around them was not.**

Tests check numbers. Nothing automated checks the sentence -- which is why this
audit is a reading pass, not a test run.
