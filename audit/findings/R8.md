## Is bipartiteness measured or asserted, at each site?

Two genuinely different quantities exist and must not be conflated with each
other:

1. **`GraphReport.bipartite`** (`src/tsu/passes/analyse.py:25,48`) -- the
   PRE-mediation logical graph's own bipartiteness. **Always measured**:
   `bip = nx.is_bipartite(G)` (`:48`), a real NetworkX call against the
   actual edge list, never inferred from the target or assumed. Serialized
   to `metrics.json`'s `"bipartite"` and `candidates.json`'s per-candidate
   `"bipartite"` field for every candidate that reached `analyse` (including
   REJECTED candidates -- e.g. a degree-exceeded candidate still has a real
   measured `bipartite` value, confirmed via `demo/receipts/l1/candidates.json`
   showing one `false` and one `true` row for the same compile).

2. **`MediationReport.bipartite_after`** (`src/tsu/passes/route.py:78`) --
   the POST-mediation graph's bipartiteness. **Measured when mediation
   actually ran**: `route.py:228`, `bipartite_after = nx.is_bipartite(G)`
   against the literal mediator-subdivided graph -- a real, independent
   re-measurement, not an assumption carried over from step 1. **But
   `insert_mediators` (and therefore this field) is only invoked at all
   when `target.bipartite.value and not report.bipartite`**
   (`place.py:287-288`) -- when the graph was ALREADY bipartite,
   `insert_mediators` is never called, `Placement.mediation` stays at its
   default `None`, and `bipartite_after` is never set to anything, not even
   the logically-trivial `True` a reader might expect ("nothing changed, so
   whatever it was before it still is"). `route.py:165-168` DOES contain a
   branch that would return `bipartite_after=True` for this exact case
   (`if report.bipartite: return ising, MediationReport(..., bipartite_after=True, ...)`),
   but this branch is **dead code from `place()`'s calling convention** --
   `place()` checks `report.bipartite` itself before ever calling
   `insert_mediators`, so that function's own "already bipartite" shortcut
   branch is unreachable from the real compile pipeline (confirmed by
   reading `place.py:287-288`'s guard, which is the only call site of
   `insert_mediators` in `src/`).

### Important

**The "fixed" pattern is honest but needlessly pessimistic: it renders
`"unavailable: field absent from receipt"` for a fact that is fully known
and already measured elsewhere in the same receipt.** For an unmediated
overlay (e.g. `elev_band`, whose `report.bipartite` was already `True` --
confirmed in `demo/receipts/elev_band/metrics.json`, `"bipartite": true`),
`self.overlay_receipt.bipartite_after` is `None` purely because
`insert_mediators` was never called (see above), NOT because the fact is
unknown -- the true post-"mediation" state is trivially the same as the
pre-mediation state (nothing was subdivided), and that pre-mediation state
IS a real, measured `nx.is_bipartite` result sitting in the SAME receipt's
`metrics.json`. `fmt_value(None)` (`lattice_app.py:1094-1095`) renders this
as `"unavailable: field absent from receipt"` -- which additionally
misdescribes WHY the value is missing: the `"mediation"` key is not absent
from `passes.json`, it is present with JSON value `null`
(`lattice_app.py:1138-1145`'s own comment establishes this distinction
correctly for `partition_method` but the SAME nuance is not carried into
`bipartite_after`'s rendering). **Concrete failure scenario:** a viewer of
the temperature-control readout for an unmediated overlay reads "0
mediator spins in this program (bipartite_after: unavailable: field absent
from receipt)" and could reasonably infer "this app does not know whether
the receipt is bipartite," when in fact `self.overlay_receipt` already
loaded the correct, measured answer (`metrics.json`'s `bipartite: true`)
into a DIFFERENT attribute that this specific readout simply never
consults. This is the converse of the original defect (which overclaimed);
this is a needless underclaim -- lower severity, but still a case of a
number that IS available being presented as if it were not, on the same
receipt, one call away. **What was checked:** traced `place()`'s guard

## Appendix J 2 -- is our placement obstruction the same phenomenon?

Read `2608.01615v1.pdf` pp.42-44 (Appendix J, sections J1-J2) directly.
The relevant passage, quoted verbatim from the extraction:

> *"Placement on the Z1 lattice adds an obstruction that is independent of
> the coupling cap. Laid out on the chessboard, the output and the hidden
> spins sit on opposite colors, and each blanket input takes the color that
> lets it reach its dominant partner. A spin that is simultaneously a
> pairwise neighbor and a three-body partner of site n needs both an affine
> edge to the output and a bilinear edge to a hidden spin, and on a
> bipartite graph it cannot keep both. The lattice topology therefore
> contributes an irreducible per-site residual even before the cap is
> imposed, so topology and cap act as two independent sources of
> compilation error."*

**Answer: related in kind, not the same mechanism, and our compiler's
actually-observed failure mode is a third, weaker thing entirely.**

- **Their obstruction** is a per-site ROLE-COLORING conflict specific to
  their meta-EBM's factorized kernel construction: a single physical site
  is asked to play two incompatible roles (an "affine" partner of the
  output spin AND a "bilinear" partner of a hidden spin) that the fixed
  2-coloring forces onto opposite colors, so one site cannot satisfy both
  roles simultaneously. This is a PROVEN, closed-form, cap-independent
  lower bound on error, derived analytically (`Kc`, `Jmax` play no role in
  its derivation) -- it exists because of what each node MEANS in their
  specific 3-body kernel factorization, not because of raw edge density.
- **Our compiler's analogous PROVEN residual** is `GraphReport.mediators`
  (`analyse.py:2-6`'s own docstring: *"the connectivity residual |E| -
  (max-cut value of G), the floor on mediator count for a bipartite
  substrate. It is a NECESSARY condition and never a sufficient one"*) --
  also a cap-independent, provable lower bound forced by bipartiteness, but
  derived from raw EDGE COUNT vs. a graph's max-cut, agnostic to any
  per-node semantic role. This is the right general-purpose analogue: both
  are "the 2-coloring constraint forces a structural cost regardless of
  cap," but the two residuals are computed from, and depend on, different
  properties of the graph (site role-typing vs. global edge-cut structure).
- **Our compiler's actually-OBSERVED failure mode** (`placement_effort_exhausted`,
  the one a user is most likely to hit) is neither of the above. It is a
  HEURISTIC GEOMETRIC EMBEDDING search running out of restarts/iterations
  when trying to assign 2-D lattice coordinates such that every edge lands
  on one of Z1's four fixed offset rules -- and `place.py`'s own docstring
  is explicit that this is "a fact about the search, not about the
  substrate" (`place.py:8-9`) and NEVER a proof (`:216-219`, `geometry_unreachable`
  -- the failure class that WOULD be a proof -- "is reserved for a case
  this pass can actually PROVE; this pass makes no such proof"). This is
  categorically weaker evidence than either paper's residual: theirs is a
  closed-form bound; ours (when it actually fires in practice) is "we tried
  a bounded, seeded random search and it did not find an embedding," which
  says nothing about whether a better search would succeed.

**Conclusion for this task's own instruction not to accept the a3
controller's framing on faith:** the controller's research
(`a3-source-research.md`) states *"Extropic's own compiler team runs into
placement obstructions, bipartite restrictions and irreducible residuals --
the same three walls this project hit and documented independently"* -- this
is directionally correct at the level of "both projects found that forcing
bipartiteness imposes an irreducible, cap-independent structural cost," and
that qualitative correspondence is real and worth stating. It is NOT correct
to say it is "the same phenomenon" at the mechanism level: their residual is
a per-site role-typing conflict from a specific 3-body kernel factorization;
ours (`|E| - MaxCut`) is a global edge-parity residual from arbitrary
pairwise density. Grepped `demo/*.py` and `src/tsu/*.py` for any place this
stronger, mechanism-level equivalence claim is actually asserted to a
viewer or in a docstring: **none found** -- the overclaim risk here is
hypothetical (in the audit's own working notes, not in the shipped
product), so no finding is filed against the codebase; this section's
purpose was to pre-empt exactly that overclaim before it could migrate from
research notes into a UI string or whitepaper claim.

**Verdict: PASS-WITH-FINDINGS.** Every live bipartiteness claim in the app
is either a documented target fact or a genuinely measured value; the one
finding is an unnecessary "unavailable" for a fact that is measured and
present elsewhere in the same receipt, not a false claim of bipartiteness
anywhere. The Appendix J comparison is genuine but qualitative, not a
mechanism-level match, and nothing in the shipped product currently claims
otherwise.
