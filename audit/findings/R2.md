## Does the live app do anything torx or Thermalizers would do, at runtime? No.

Confirmed by two independent instrumentation methods this wave (`dependency_map.md`'s
`sys.settrace` map, and `R1.md`'s monkeypatched sentinels, which additionally
wrapped the real `torx` package's own public constructors, not just this
project's narrow `torx_backend` wrapper): **zero** calls into `torx`, in either
direction, across one full unclamped tick and one full clamped batch. `torx`
exists in this codebase in exactly one place
(`src/tsu/backends/torx_backend.py`), used only as a **compile-time-only,
narrow-scope independent oracle**: it drives Extropic's own `PISING` generator
gate to stationarity under their `StateVectorSimulator` to get an exact reference
density for a single-bond (2-node/1-edge) model, explicitly stated by its own
module docstring to be exact *only* for that narrow case, and it is called from
exactly one place in `src/` (`search.py:520,724`, inside `_verify`), a
compile-time pass this audit is barred from invoking (`tsu compile` forbidden)
and which the live app never reaches (`search`, `_verify`, and `compile_spec`
all confirmed 0 occurrences in every live draw traced, `R1.md`).

## The precise, defensible answer

**What we genuinely share with Extropic's stack:** the low-level execution
substrate. thrml is used **as intended**, for exactly what it is documented to
do -- block-Gibbs sampling of an Ising energy-based model over chromatic colour
blocks -- and the topology this project targets (degree 16, bipartite, the
specific `(1,0),(2,1),(2,3),(4,1)` offset rules) is now independently confirmed
to match the Z1 chip's own documented connection rules (`audit/provenance.md`
Part 2), not a project invention. This is real and substantial, not a surface
resemblance.

**What we do differently, by design:** LATTICE's front end compiles declarative
constraints (a spec of variables, domains, and rules), never a Torx program of
stochastic kernels -- these are different *kinds* of input language solving an
analogous problem (get a workload onto a Z1-shaped bipartite lattice), not the
same language used two ways. Our embedding technique for couplings the topology
can't realise directly (mediators, edge subdivision, one hidden spin per
frustrated edge) is related to but not the same as Thermalizers' chain embedding
(node subdivision, a chain of physical p-bits per logical spin) -- the two must
never be described as interchangeable or as this project "implementing"
Thermalizers' method, because they subdivide a different graph element for a
different reason.

**What we must never claim:** that this compiler runs on, is compatible with, or
implements Torx or Thermalizers -- Thermalizers is not released as a library at
all (whitepaper only, *"LIBRARY COMING SOON"*), so there is nothing to be
compatible *with* yet; and torx, where it does appear in this codebase, never
executes in the path a user actually exercises, confirmed twice, independently,
this wave. The correct, defensible framing is: **LATTICE and Thermalizers solve
an analogous problem for the same class of target hardware, using genuinely
different front-end techniques, and independently arrived at some of the same
structural obstructions** (placement obstruction distinct from the coupling cap;
an irreducible per-site residual; the bipartite chessboard blocking dense
graphs) -- which is real evidence this project's approach is not naive, but is
evidence of **convergent, independent design**, not of shared implementation.

## Update 2026-09-10 — new evidence on the coupling-parameter ratio (still UNRESOLVED)

This finding recorded a 9.988:1 ratio between the die's implied edge count
(269,568 pbits x 16 / 2 = 2,156,544) and the 215,904 "coupling parameters" in
Fig. 05's caption, and noted that no source explains it.

**What is new:** the project previously held only the CAPTION of Fig. 05. The
figure's own callout block, supplied 2026-09-10 from
https://extropic.ai/writing/from-one-to-one-billion, carries a second number the
caption does not:

```
PBITS                        269,568 IN 8 CORES
COUPLERS (PBIT-PBIT EDGES)   2,135,904 UP TO 16 PER PBIT
```

So the figure states BOTH `2,135,904` couplers (callout) and `215,904` coupling
parameters (caption).

**Evidence that they are different quantities (weight sharing is real):**
- The two use different terms, and the callout explicitly parenthesises
  "(PBIT-PBIT EDGES)" as though distinguishing itself from something else.
- Driving many physical couplers from fewer programmable parameters is ordinary
  hardware practice; configuration SRAM is expensive.
- 2,135,904 is within 0.96% of the computed 2,156,544 (deficit 20,640),
  exactly the shape of a boundary correction where edge pbits have fewer than
  16 neighbours. That makes the CALLOUT a credible physical edge count, which in
  turn makes the caption's number something else.

**Evidence that the caption is a transcription error:**
- `215,904` is `2,135,904` with the digit `3` deleted -- exactly, not
  approximately.
- The relationship recurs after factoring out the shared 2^5 * 3 = 96:
  22,249 vs 2,249, again a single-digit deletion.
- The ratio is 9.8928, not a clean divisor. A real sharing scheme ties
  parameters across a fixed structural group and would produce an integer
  ratio; 9.8928 corresponds to no obvious grouping of a degree-16 lattice.
- R9 grepped the full 55-page Thermalizers extraction for "215,904": zero
  matches. The number exists only in this caption.

**Status: STILL UNRESOLVED.** The evidence has sharpened into two specific
competing hypotheses rather than one unexplained number, but neither is
established. Controller's read is roughly 70/30 toward transcription error;
that is a judgement, not a finding.

**What would settle it**, in order of decisiveness: the blog's BODY TEXT near
Fig. 05 repeating either number in prose; any other Extropic material giving a
coupler count independently; or a per-core figure, since 2,135,904 / 8 = 266,988
and 215,904 / 8 = 26,988 and a core-level citation of either decides it.

**Why it still matters:** unchanged from the original finding. This project's
compiler assumes one independently-programmable J per edge throughout. Under the
sharing hypothesis that assumption is wrong for the physical Z1 die, and wrong
SILENTLY -- no gate, test or receipt in this project would detect it. Nothing
currently depends on resolving it, and it stays parked rather than assumed away.

Separately and NOT in doubt: `269,568` pbits appears in both the callout and the
caption. `target.py`'s `node_budget` has been updated from the Thermalizers
paper's approximate "~250,000" (F-15) to that exact figure.

## New open question 2026-09-10 — the die is 8 CORES, and this project models it as one lattice

Raised while reading the Z1 systems material. Same class as the coupling-parameter
question above: an undocumented structural assumption that would fail silently.

**The facts.** Fig. 05: "269,568 PBITS IN 8 CORES". The die image shows eight
core blocks with visible links between them. 269,568 / 8 = 33,696 pbits per core,
and 33,696 = 156 x 216 -- a clean rectangular decomposition.

**What this project assumes.** `target.py`'s z1 profile describes ONE uniform
lattice: offsets (1,0),(2,1),(2,3),(4,1) plus their rotations, degree 16, max
reach 4 cells, and `node_budget = 269,568`. There is no notion of a core boundary
anywhere in the profile or in `place.py`'s grid embedder.

**Why that may not hold.** If the eight cores are separate lattices with
RESTRICTED connectivity between them -- rather than one continuous 269,568-node
lattice -- then a model larger than ~33,696 nodes cannot be placed the way this
project assumes, and `_try_grid_embed`'s success on a large graph would be a
statement about an idealised lattice rather than about Z1.

**What is and is not established.** `node_budget = 269,568` is correct as a count
of pbits on the die; that is cited and not in doubt. What is NOT established is
that all 269,568 are reachable as a single uniform degree-16 lattice for
PLACEMENT purposes. This project has never distinguished those two claims.

**Severity.** Lower than the coupling-parameter question for current work,
because every model this project has actually compiled is far below 33,696 nodes
-- the 64x64 world layers are 4,096. It becomes load-bearing the moment anything
targets a substantial fraction of the die, and it is exactly the sort of
assumption that looks fine until it does not.

**What would settle it:** any Extropic material describing inter-core
connectivity, or a per-core offset/degree statement. Failing that, the
conservative move is a second profile (`z1_core`) with `node_budget = 33,696`,
used when a model must be certain of placement, leaving the full-die profile for
counting.

**Not acted on.** Recorded rather than fixed: no current work depends on it, and
inventing a core-boundary model without a source would be exactly the kind of
guess this file exists to refuse.

## 2026-09-10 — edge-count reconstruction largely answers the core question

Derived here rather than sourced. Reproducible from the offset rule alone.

**Method.** For a W x H grid and the documented offset set (the 16 rotations of
(1,0),(2,1),(2,3),(4,1)), the edge count is
`E = 1/2 * sum over offsets of max(0, W-|dx|) * max(0, H-|dy|)`.
Brute-forced over EVERY rectangular tiling with W*H = 269,568 (one connected
array) and every tiling with W*H = 33,696 at 8 isolated cores, comparing against
Fig. 05's callout figure of 2,135,904 couplers.

| hypothesis | best fit | diff from 2,135,904 |
|---|---|---|
| one connected array | 216 x 1248 | **+168** (0.008%) |
| " | 208 x 1296 | -392 |
| 8 isolated cores | 8 x (162 x 208) | -20,608 (~1%) |
| " | 8 x (156 x 216) | -20,832 |

**Result.** Every connected tiling lands within a few hundred edges; every
isolated-core tiling undercounts by ~20,000 or more. That deficit is exactly what
isolating the cores would delete: 14 of the 16 offsets reach across a horizontal
boundary with reaches summing to 14, so a ~216-wide boundary carries ~3,024
couplings, and 8 cores in a 2x4 mesh have 7 internal boundaries -- ~21,000 edges.
The observed deficit MATCHES the predicted one.

**Conclusion for the core question:** the callout is consistent with a CONNECTED
array and inconsistent with eight isolated cores. This project's single-lattice
model is better supported than the open question above assumed. Downgraded from
"open architectural risk" to "consistent with our model, specific geometry
unidentified."

**Two caveats, stated because they matter.** No geometry reproduces 2,135,904
EXACTLY -- the closest is +168. And the best-fitting aspect ratios (216 x 1248 is
5.8:1) are implausible for a die under 12 mm square, so the real array is
probably not a plain rectangle; the die image shows a central structure that
could displace pbits. **The geometry CLASS is discriminated; the geometry is
not.** No claim is made here about the actual floorplan.

**Bearing on the coupling-parameter question:** this confirms 2,135,904 is a
genuine physical edge count, since it reconstructs to within 0.008% of a real
lattice, and 215,904 is an order of magnitude too small to be any edge count of
this die. That was already the easier half. It does NOT discriminate
transcription-error from genuine parameter sharing, so that question is unmoved
at roughly 70/30.

**Cheapest decisive action for both, unchanged:** ask Extropic directly.

## 2026-09-10 — WORKING ASSUMPTION ADOPTED: connected chip-level fabric

Adopted deliberately by Paul, on the strength of the edge-count reconstruction
above. Recorded here as an ASSUMPTION with its evidence and its failure mode, not
as a fact.

**The assumption, in the form the evidence actually supports:**

> The published coupler count is consistent only with a connected chip-level
> p-bit coupling fabric, not with eight independent stochastic processors.

Note the wording. The public documentation does NOT state this. It states four
numbers -- 269,568 pbits, 8 cores, 16-neighbour connectivity, 2,135,904 couplers.
Connectivity is DERIVED from those under the documented offset rule: every
isolated-core tiling undercounts the published coupler figure by ~20,600-21,500,
matching the independently predicted boundary deficit of ~21,000 (7 internal
boundaries in a 2x4 mesh, ~3,024 couplings each). Stating it as a derivation
rather than as documentation means that if Extropic later contradicts it, the
exact inference that broke is identifiable.

**What it licenses:** treating `node_budget = 269,568` as PLACEABLE and not
merely countable, and trusting `_try_grid_embed` on graphs above one core's
33,696 nodes.

**What it does NOT license:** any claim about inter-core BANDWIDTH, any claim
that the array is a plain rectangle (nothing reproduces 2,135,904 exactly; the
best fit is +168 at an implausible 5.8:1 aspect ratio), and any claim about how
cores are addressed.

**The important part: this project was ALREADY assuming it, silently.**
`node_budget = 269,568` and `place.py`'s grid embedder have always treated the
die as one lattice, with nothing anywhere recording that as a choice. Adopting
the assumption changes no behaviour; it makes an invisible assumption visible.
That is the whole value of the change.

**Queued implementation** (not yet done -- target.py was being edited concurrently
for the C-1 comment fix):
  1. `connected_fabric` on the z1 profile as `Sourced(True, "assumed", ...)`,
     carrying the derivation and the ~21,000-edge argument in its quote, so it
     flows through `is_assumed()` and prints ASSUMED like every other unsourced
     value -- the same mechanism that stopped |b| <= 6.0 reading as a hardware
     fact.
  2. `preflight` surfaces it ONLY for models above 33,696 nodes. Below one core's
     worth the assumption cannot affect placement, and warning on every 4,096-node
     world layer would train readers to ignore it. The first model that actually
     depends on it is the first one told.

**Failure mode if wrong:** a model between 33,696 and 269,568 nodes would be

## 2026-09-14 — RESOLVED: the two coupling figures are DISTINCT quantities

This question was parked twice above at roughly 70/30 toward "transcription
slip". **That reading was wrong.** Both numbers appear in Extropic-authored prose
as different quantities.

**The citation**, `https://extropic.ai/writing/z1t/`, body prose (not a caption):

> "For Z1 specifically, this graph of couplings has each node being of degree 16,
> for a total of **269,568 pbits** and **2,135,904 coupling edges** on a single
> chip."

And, in the die callout on the same page and in `from-one-to-one-billion`'s
Fig. 05 caption: *"269,568 pbits, **215,904 coupling parameters**"*.

So: **2,135,904 coupling EDGES, 215,904 coupling PARAMETERS.** Ratio 9.89:1.
Not a slip. The die has roughly ten times more physical edges than programmable
parameters.

### How this project got it wrong, and the lesson

Found by the second agent (Grok) on the live page. The controller searched local
PDF snapshots for the literal string `2,135,904`, got **zero hits across every
Extropic PDF**, and reported that as contradicting evidence.

**That zero was a tooling artifact.** Extropic sets those figures in bold, and
the PDF extractor doubles every glyph inside a bold run. The raw extraction reads:

    2 2, ,1 13 35 5, ,9 90 04 4 c co ou up pl li in ng g e ed dg ge ess

which de-doubles to exactly `2,135,904 coupling edges`. The grep could never have
matched. Searching for the *prose* around it (`"graph of couplings"`,
`"single chip"`) finds the sentence immediately in the same local PDF.

**Absence of evidence from an unvalidated tool is not evidence of absence.** The
controller nearly used a broken search to refute a correct finding, having spent
the session insisting that external findings be verified rather than trusted --
and then failed to verify its own instrument. A negative result needs its method
checked at least as hard as a positive one.

### The consequence for this compiler, which is real

`tsu` assumes **one independently-programmable `J` per edge**, everywhere. If
physical Z1 exposes ~215,904 parameters across ~2,135,904 edges, that assumption
does not hold on the physical die, and a model requiring many distinct coupling
values may be unprogrammable **in a way no gate or test in this project detects**.

**What is now known:** the two counts, and their ratio.
**What is still unknown:** the *mapping* -- which edges share a parameter, and
whether the sharing is structured (by offset class, by core, by tile) or
arbitrary. Nothing published explains the mechanism. A weight-tying hypothesis
was tested against the Thermalizers paper earlier in this file and failed.

Because the mechanism is unknown, this project models the **count** and refuses
to invent the **mapping**: `target.py` now carries `coupling_parameters` as a
sourced figure and `per_edge_independent_J` as an explicit assumption, so the
idealisation is stated rather than silent.

## Standing principle (Paul, 2026-09-14): they have silicon; we have a simulator

> "Extropic has actual hardware so don't dismiss what they say as any error or
> anything. They may have observed hardware behaviors that don't surface through
> THRML or sim."

This is a correction to how this project reasoned about the coupling-parameter
question, and it is recorded as a standing rule because the situation recurs.

**What happened.** Extropic's published figures disagreed with this project's
model of their die. The controller's response was to weigh the evidence and land
at roughly 70/30 that *they had made a transcription error*. That prior was
backwards. The correct posture, when a party with a fabricated chip states
something our CPU simulation cannot account for, is that **they are describing
behaviour we have not observed**, not that they mis-typed.

**Why this is not deference.** It is a question of what each side has access to.
thrml simulates an idealised block-Gibbs sampler; it has no notion of coupler
circuitry, configuration SRAM, process variation, or anything else that decides
how a real die exposes programmable parameters. A discrepancy between our model
and their statement is therefore evidence about OUR MODEL first. Treating it as
evidence about their copy-editing inverts the epistemics.

**The rule going forward.** When published Extropic material disagrees with this
project's model of the hardware:

1. Mark the affected assumption **ASSUMED / UNVERIFIED** in `target.py`, so it
   surfaces in every report that gates on it.
2. **Ask.** A one-line question costs them nothing and settles it.
3. **Never invent the mechanism** to make the simulation look complete. An
   invented mapping that reconciles the numbers would be worse than the open
   question, because it would be wrong silently and no test here would catch it.

This is the same discipline the rest of this project applies to its own numbers,
pointed in the one direction it had not been: `unavailable` with a reason beats a
confident answer, and that holds for claims about someone else's hardware most of
all.

Currently open under this rule: numeric `h_max` (the only assumed gate in the
verification pack), and the coupling-parameter **sharing structure** -- which
edges share a parameter, and whether the sharing is structured or arbitrary.
