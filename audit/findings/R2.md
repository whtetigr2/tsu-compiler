grounded in code (`file:line`) and in the primary-source PDFs already extracted

## Does the live app do anything torx or Thermalizers would do, at runtime? No.

Confirmed by two independent instrumentation methods this wave (`dependency_map.md`'s
`sys.settrace` map, and `R1.md`'s monkeypatched sentinels, which additionally
wrapped the real `torx` package's own public constructors, not just this
project's narrow `torx_backend` wrapper): **zero** calls into `torx`, in either
direction, across one full unclamped tick and one full clamped batch. `torx`
exists in this codebase in exactly one place
(`src/tsu/backends/torx_backend.py`), used only as a **compile-time-only,
narrow-scope independent oracle**: it drives Extropic's own `PISING` generator
gate to stationarity under their `StateVectorSimulator` to get an exact reference
density for a single-bond (2-node/1-edge) model, explicitly stated by its own
module docstring to be exact *only* for that narrow case, and it is called from
exactly one place in `src/` (`search.py:520,724`, inside `_verify`), a
compile-time pass this audit is barred from invoking (`tsu compile` forbidden)
and which the live app never reaches (`search`, `_verify`, and `compile_spec`
all confirmed 0 occurrences in every live draw traced, `R1.md`).

## The precise, defensible answer

**What we genuinely share with Extropic's stack:** the low-level execution
substrate. thrml is used **as intended**, for exactly what it is documented to
do -- block-Gibbs sampling of an Ising energy-based model over chromatic colour
blocks -- and the topology this project targets (degree 16, bipartite, the
specific `(1,0),(2,1),(2,3),(4,1)` offset rules) is now independently confirmed
to match the Z1 chip's own documented connection rules (`audit/provenance.md`
Part 2), not a project invention. This is real and substantial, not a surface
resemblance.

**What we do differently, by design:** LATTICE's front end compiles declarative
constraints (a spec of variables, domains, and rules), never a Torx program of
stochastic kernels -- these are different *kinds* of input language solving an
analogous problem (get a workload onto a Z1-shaped bipartite lattice), not the
same language used two ways. Our embedding technique for couplings the topology
can't realise directly (mediators, edge subdivision, one hidden spin per
frustrated edge) is related to but not the same as Thermalizers' chain embedding
(node subdivision, a chain of physical p-bits per logical spin) -- the two must
never be described as interchangeable or as this project "implementing"
Thermalizers' method, because they subdivide a different graph element for a
different reason.

**What we must never claim:** that this compiler runs on, is compatible with, or
implements Torx or Thermalizers -- Thermalizers is not released as a library at
all (whitepaper only, *"LIBRARY COMING SOON"*), so there is nothing to be
compatible *with* yet; and torx, where it does appear in this codebase, never
executes in the path a user actually exercises, confirmed twice, independently,
this wave. The correct, defensible framing is: **LATTICE and Thermalizers solve
an analogous problem for the same class of target hardware, using genuinely
different front-end techniques, and independently arrived at some of the same
structural obstructions** (placement obstruction distinct from the coupling cap;
an irreducible per-site residual; the bipartite chessboard blocking dense
graphs) -- which is real evidence this project's approach is not naive, but is
evidence of **convergent, independent design**, not of shared implementation.

## Findings

### Important

**T-1: The app-facing disclosure of the torx/Thermalizers relationship is
thinner than what this audit found, and nowhere on screen states the two most
load-bearing facts** (torx never executes live; Thermalizers has no released
library to be compatible with). `demo/explainer.py` and `FOOTER_TEXT`
(`lattice_app.py:125-127`) discuss Extropic's hardware caps and disclaim
specific numbers, but neither mentions torx, Thermalizers, or the
declarative-constraints-vs-kernels distinction at all -- a viewer reading the
app's own "what is this" material has no way to learn what this project's
correspondence to Extropic's software stack actually is, or is not, only what
it claims about the hardware target. **Concrete failure scenario:** a viewer
(or a future engineer) infers from LATTICE's Extropic-hardware framing that it
also implements or extends Extropic's *software* stack (Torx/Thermalizers),
which this table shows is not true in either direction. **What was checked:**
`grep -in "torx\|thermalizer" demo/*.py` -- zero hits anywhere in `demo/`,
confirming the correspondence is not explained to a viewer anywhere in the
running app, only in this audit's own documents and in source comments a
viewer never sees.

### Minor

**T-2: The mediator-vs-chain-embedding distinction, load-bearing for this
correspondence table, exists only in `route.py`'s own module docstring and this
audit's documents -- not in any user-facing text.** Not a defect in the code
(the docstring, `route.py:1-45`, is accurate and detailed) -- recorded because a
future contributor relying on `demo/explainer.py` alone (the app's own
"what is this" surface) would not learn that mediators and chain embedding are
different techniques, only that mediation exists.

### What was tried and did not turn up a finding

- Checked whether `thrml_backend.py`'s use of thrml's API deviates from thrml's
  documented contract anywhere (e.g. hand-rolling a Gibbs step instead of calling
  `sample_states`, or constructing `IsingEBM` with a non-standard sign
  convention) -- read the full file (`src/tsu/backends/thrml_backend.py`,
  180 lines); every energy/sampling call routes through thrml's own
  `IsingEBM.energy`/`sample_states`, confirmed by the file's own docstring
  claim ("Exact references come from IsingEBM.energy, never a hand-written
  Boltzmann loop -- WL4-WL7 were computed by hand while that method sat unused,
  and retrofitting them reproduced every number to 1e-9") and by direct reading
  of `_model`/`sample_chains`/`sample`/`exact_distribution`. No finding: thrml is
  used as intended throughout, including in the zero-edge special case
  (`_edgeless_sample`/`_edgeless_distribution`), which is documented as a
  deliberate bypass of a specific thrml vendor-code `IndexError` on empty edge
  blocks (`thrml_backend.py:8-18`), not a general avoidance of thrml.
- Checked whether `torx_backend.py` computes anything itself rather than

  *"An earlier draft of this file imported torx and then computed a numpy

  `torx_cross_check` in full (`torx_backend.py:41-87`); it builds a real
  `DiscretePCircuit([PISING([0,1])], reps=reps)`, compiles it through torx's own
  `StateVectorSimulator`, and iterates `reps` until convergence -- genuinely
  torx's own machinery, not a numpy stand-in. No finding.
- Checked whether Thermalizers' chain-embedding numbers (18 p-bits/chain,
  1774/336, 3140 couplings) are used anywhere in this codebase as if they applied
  to our mediator counts -- `grep -n "18\b" src/tsu/passes/route.py demo/*.py`
  and a read of every mediator-count display site
  (`demo/lattice_app.py`'s FRONTIER/LIVE LATTICE panels) -- no numeric borrowing
  found; our mediator counts (64 for this receipt) are always our own compiler's
  own measured output, never Thermalizers' example figures. No finding.
