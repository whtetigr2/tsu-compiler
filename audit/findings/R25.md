# R25 -- the most hardware-native model there is, is the one that will not compile

**Status:** FOUND, open. Not a retraction -- nothing false was published. A
capability gap, measured while asking what a LEARNED creature model would look
like on Z1.

## What was being asked

The game's creature bodies are generative: no correct answer, diversity is the
product. That is the same shape as Extropic's own shelf workloads
(`prog_codon_opt_tiny` reports `diversity_distinct 641` of `729` reachable, all
valid) and the shape their hardware is actually for. So: replace the ten
hand-written anatomy constants with LEARNED couplings, trained by contrastive
KL through thrml's `estimate_kl_grad`.

That needs latent nodes. The canonical shape is an RBM.

## Degree is not the problem, and that was the first surprise

    shape                          spins  edges   deg  verdict  gate
    dense, 16 latents                331   5040   315     fail  max_degree
    dense, 256 latents               571  80640   315     fail  max_degree
    sparse (random), 256 lat, fo 8   571   2520    19     fail  max_degree

A dense RBM fails on the LATENTS, not the visible layer: a hidden unit that
sees the whole 315-cell body has degree 315 no matter how few hidden units
there are. Random sparsity fails too -- fanout 8 over 256 latents averages 9.8
fan-in but spikes to 19.

Balanced round-robin assignment fixes degree completely:

    320 latents, fanout 8            635   2520     8     fail
    1024 latents, fanout 16         1339   5040    16     fail

Degree 8 and 16, inside the cap. Every gate passes -- degree, |J|, |b|,
colouring, node budget. Still fails.

## The real constraint is geometry

    embedding   failed
    placed      False
    place_error placement failed: placement effort exhausted

Z1 does not offer "sixteen neighbours of your choosing". It offers sixteen
SPECIFIC relative positions:

    (-4,-1) (-3,2) (-2,-3) (-2,-1) (-1,0) (-1,2) (-1,4) (0,-1)
    (0,1)   (1,-4) (1,-2)  (1,0)   (2,1)  (2,3)  (3,-2) (4,1)

Degree <= 16 is necessary and nowhere near sufficient. A model wired for
machine-learning reasons -- dense, random, round-robin -- has no spatial
structure to lay onto that pattern.

## So take the stencil as the architecture. It still will not place.

Build the model whose interaction graph IS the die's stencil: nodes on a W x H
grid, edges at exactly those sixteen offsets. The identity map v(x,y) -> (x,y)
realizes every edge BY CONSTRUCTION, so it is provably embeddable.

    grid     spins  edges  deg  placed  verdict
    15x21      315   2040   16   False     fail
    24x24      576   3960   16   False     fail
    32x32     1024   7320   16   False     fail

This is the same defect class C1 already fixed once for plain grids, whose own
docstring in `passes/place.py` says that reporting three provably-embeddable
grids as geometry_unreachable is "the exact representation-vs-hardware
conflation this project exists to prevent."

`_try_grid_embed` is the structural fix for that -- but it hardcodes
`_GRID_UNIT`, the four axis-unit steps. A stencil graph has edges like (-4,-1),
so the fast path declines, and the annealer then hunts for what the identity
map gives away free.

## Why the obvious fix does not work

Generalising `_try_grid_embed` to take the target's offset set is correct -- the
stencil is symmetric, eight pairs and their negations, which the candidate
intersection requires -- and it still fails. Measured why:

    offset pairs that are themselves one offset apart: 0 of 120

The stencil is TRIANGLE-FREE. No two neighbours of a node are neighbours of
each other, which is sensible for a sampling fabric since it kills every
3-cycle, and is almost certainly deliberate. But the backtracking forces a
position only when a node has two or more already-placed neighbours, and here it
never does: each of the root's sixteen neighbours has sixteen independent
choices. Local constraint propagation has nothing to propagate.

The generalisation was reverted rather than shipped: correct, costs ~79s per
failure, and helps no case that has been measured.

A real fix needs a GLOBAL method -- recovering lattice coordinates from the
graph algebraically rather than growing an embedding locally. Scoped, not
attempted.

## What this means

The compiler places simple grids, and models needing mediation. It cannot place
a model that exploits Z1's full connectivity, which is precisely the class a
learned EBM would live in. Every claim made so far stands -- the game is a
4-neighbour grid and places in 0.7s -- but the learned direction is blocked on
this.

## A second constraint, unmeasured

A learned model needs every edge independently programmable. The balanced RBM
needed 2,520 distinct coupling values, the stencil model 2,040; the game's
visibility model needs 2. `preflight`'s own note: Z1 has 215,904 programmable
parameters for 2,135,904 edges -- about 9.9 edges sharing each -- and the
sharing structure is unpublished, so `per_edge_independent_J` is an ASSUMPTION,
not a fact.

Hand-designed models with a handful of distinct couplings do not care. Learned
models care completely. Whether Z1 can carry per-edge learned weights is a
question for Extropic, and it decides whether learned EBMs fit this hardware at
all or only hand-designed ones do.
