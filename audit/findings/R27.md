# R27 -- a search that gave up is reported as a hardware limit

**Status:** FOUND, open. Not a retraction, and nothing published is false. This
is a mislabel inside the compiler, of exactly the class this project exists to
prevent, plus a consequence: the default budget ships a larger model than
necessary.

Surfaced while chasing R26. Measured, not reasoned about.

## The measurement

`programs/seq_design_longer.yaml`, compiled through `passes.search.compile_spec`
against the `z1` profile, varying only the placement budget:

    placement budget      selected      domain_wall state        physical spins
    default (6, 40k)      one_hot       HARDWARE_INFEASIBLE      32
    (24, 250k)            domain_wall   SELECTED                 24

Both carry 8 mediators. The second compile is 25% smaller on the die. It costs
about 32 seconds against about 5.

The encoding the compiler selects is therefore **not a function of the spec and
the target alone**. It is a function of the spec, the target, and how hard the
placement search was allowed to try.

## The mislabel

At the default budget, the domain-wall candidate is recorded as
`HARDWARE_INFEASIBLE`. Its own attached failure says something different:

    failure_class = 'placement_effort_exhausted'
    reason        = 'placement failed: placement effort exhausted'
    remediations  = ('increase placement effort',
                     'more restarts, more iterations per restart, or a larger
                      patch may find an embedding within budget', ...)

The hardware is not the limit. The search is. And the proof is in the table
above: the same encoding, same target, same spec, places cleanly when given more
effort, and is then SELECTED over one-hot.

`CandidateState` has eight members and none of them means "not found within
budget", so a search failure falls into the hardware bucket:

    GENERATED, SEMANTICALLY_INVALID, SEMANTICALLY_VALID, HARDWARE_INFEASIBLE,
    COMPILER_ERROR, HARDWARE_FEASIBLE, SELECTED, VIABLE_NOT_SELECTED

This is the defect `passes/place.py`'s own docstring names, quoted in R25:
reporting provably embeddable models as unreachable is "the exact
representation-vs-hardware conflation this project exists to prevent." C1 fixed
it once for plain grids. It survives here, one level up, in how a candidate's
outcome is recorded rather than in whether an embedding is found.

Anyone reading a receipt sees `domain_wall: HARDWARE_INFEASIBLE` and concludes
Z1 cannot carry that model. Z1 can.

## What this costs

Three separate things, in increasing order of seriousness.

1. **Receipts overstate the die footprint.** `prog_seq_design_longer` ships at
   32 spins. The same program fits in 24.
2. **A published claim is wrong in the narrow case.** Not one that left this
   repository, but "hardware infeasible" is a claim about Extropic's silicon,
   made on the basis of a timer.
3. **It is silent.** Nothing fails. The compile succeeds, reports COMPILED,
   selects a valid encoding, and produces a correct receipt for a larger model.
   There is no error to notice.

## The counter-argument, which is also measured

"Search longer and you will find it" is true here and is NOT true in general.
R25 is the counterexample and it is in this repository: the stencil-shaped graph
is *provably* embeddable by the identity map, and the annealer still cannot find
it, because the stencil is triangle-free and local constraint propagation has
nothing to propagate. That generalisation was reverted precisely because it cost
about 79 seconds per failure and helped no measured case.

So budget is the binding limit sometimes and the method is the binding limit
other times, and the compiler currently cannot tell you which. That distinction
is the whole content of this finding.

## What would fix it

Three changes, cheapest first.

1. **Name the state honestly.** Add a `PLACEMENT_EFFORT_EXHAUSTED` candidate
   state, or record the `failure_class` alongside the state wherever a candidate
   outcome is rendered, so "we did not find it" never reads as "it cannot
   exist."
2. **Escalate in the compiler, not only in the application.** The Observatory
   already climbs a ladder, `(6, 40k) -> (24, 250k) -> (48, 800k)`, because a
   published Extropic workload was being reported as a failure at the cheapest
   tier. `compile_spec` does not climb it, so encoding selection is decided at
   the cheapest tier and a smaller model is left on the table.
3. **Record the budget in the receipt** next to the selected encoding, so a
   reader can see that the choice was effort-dependent rather than intrinsic.

Not attempted here. Item 1 is a small change with wide blast radius through
receipt rendering; item 2 changes compile times everywhere and wants a
deliberate default.
