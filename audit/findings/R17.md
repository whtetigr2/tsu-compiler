# R17 -- Reproducibility and provenance

**Scope.** Given a receipt and a seed, is a run reproducible? Is the seed policy
recorded? Can a committed figure be regenerated from what is in the repo?
**Actually tried, not reasoned about** -- every claim below is backed by a
command actually run this task, with its real output, not an inference from
reading code.

## Test 1: is sampling reproducible given a receipt and an explicit seed? YES, verified twice, at two levels of rigour

`audit/r17_reproducibility_check.py` (run this task, output in
`audit/traces/r17_reproducibility_report.json`):

**TEST A -- same process, double call.** `tsu.simulate.simulate(receipt,
seed=999, clamp={"g0_0": 0}, n_chains=6, n_samples=3, n_warmup=600,
steps_per_sample=4)` called twice in one interpreter: raw draw arrays
bit-identical (`np.array_equal == True`, shape `(18, 192)`), `IsingModel`
weights/biases identical, and `simulation.json`'s full content identical except
`wall_time_s` (0.983s vs 0.367s -- expected to differ, carries no scientific
content).

**TEST B -- two independent, freshly-launched processes (the meaningful check,
since same-process determinism can hide a global-state dependency).**
`audit/_r17_worker_subprocess.py` spawned twice via `subprocess.run`, each a
brand-new Python interpreter, each calling the identical `simulate(..., seed=999,
...)`, each writing its own result file
(`audit/traces/r17_proc{A,B}.json`, containing the full raw draw array, not just
a summary). Independently re-diffed this task, directly, rather than trusting
the script's own self-report:

```
shapes (18, 192) (18, 192)
array_equal True
procA seed used (params.seed): 999
procB seed used (params.seed): 999
procA task_validity 0.2222... procB task_validity 0.2222...
```

Every field except `wall_time_s` (0.978s vs 0.961s) matched exactly across two
independent process launches. **This directly answers the coordinator's second
probe: jax/thrml's PRNG threading is deterministic across processes for
identical inputs.** No dependence on wall-clock, `id()`, dict ordering, or
thread scheduling was found -- `jax.random.key(seed)` (the only entropy source
`thrml_backend.sample_chains` uses, `src/tsu/backends/thrml_backend.py:213-218`)
produced byte-identical downstream draws in two processes that share nothing
but the Python source and the seed integer.

**Scope of what this establishes, stated precisely:** reproducibility holds for
the *sampling primitive* (`simulate()`/`thrml_backend.sample`/`sample_chains`)
given an explicit seed. It says nothing about compile-time reproducibility
(`compile_spec`, `place`, `route`, `search`) -- that is `UNAVAILABLE: cannot be
tested without running tsu compile, which this audit is barred from running`.

## Test 2: does the live app record the seed it actually used, or only the seed it was configured with? BOTH, with one real gap

**The per-draw actual seed IS recorded, precisely, not merely a configured
intent.** `_run_unclamped_tick` computes `seed = self.seed_base +
self.draw_counter` and `_run_clamped_batch` computes `seed = self.seed_base +
self.batch_counter` (`demo/lattice_app.py:1405,1433`) -- the literal integer
passed to `thrml_sample`/`simulate()` -- and that exact value is threaded into
every pushed message (`classify_draw(receipt, row, seed)` ->
`{"kind": ..., "seed": seed, ...}`, `demo/lattice_app.py:1238-1255`). A `valid`
message's seed is captured into `self.last_valid_seed` (`lattice_app.py:1423`),
which `_on_save_world` writes verbatim into the saved world file's `seed` field
(`worldfile.save_world(..., seed=seed, ...)`, `lattice_app.py:4014-4020`) --
confirmed by reading `worldfile.py` in full (`demo/worldfile.py:67-101`): the
saved JSON is exactly the actual seed, clamp, sampler params, spec name, and
receipt path this specific grid came from, not a name or a description of them.
**This part of the provenance chain is done correctly and is the strongest
positive finding in this section.**

**The gap: the session's very first `seed_base` is never logged anywhere a
user can see, unlike every subsequent reseed.** `LatticeApp.__init__` starts the
first worker with `self._start_worker(random.randint(0, 2**31 - 1))`
(`demo/lattice_app.py:2170`) -- no accompanying `self._log(...)` call. Contrast
this with the two other places `seed_base` is rerandomized:
`_new_seed` (`:4451-4454`) and `_restart_sampling_for_clamp_change`
(`:4489-4492`), both of which immediately log
`f"--- new seed base={new_seed_base} ... ---"` / `f"--- pins changed: ...
seed={new_seed_base} ---"` to the on-screen SAMPLE LOG. **Concrete failure
scenario:** a user launches the app, watches the very first batch of draws
stream by (before ever clicking "New seed" or changing a pin), and never sees
the initial `seed_base` anywhere in the UI -- not in the log, not in any panel.
If that user then saves a valid world from that first batch, the correct seed
IS captured (per-draw `seed`, not `seed_base`, is what gets saved, and it is
computed correctly regardless of whether `seed_base` itself was ever logged) --
so the WORST case is narrower than "unreproducible": it is "a user who does not
save a world, and only reads the log panel, cannot learn the first batch's seed
after the fact." Still a real gap in a stated design goal (the log panel exists
specifically to record what happened), and asymmetric with the two other
reseed paths for no evident reason.

**Also checked: is the seed policy documented anywhere a user reads?** No.
`grep -n "seed" demo/explainer.py` (the app's own "what is this?" window) --
zero hits. `FOOTER_TEXT` (`lattice_app.py:125-127`) does not mention seeds
either. A user has no in-app text explaining that each session gets a random
seed, that reseeding is logged, or that "Save world" is the durable
provenance mechanism.

**Ran, this task, in the foreground:**

Output: `drew 480 samples: 6 non-codewords, 350 codewords failing the contract,
124 VALID WORLDS (25.8%) ... wrote demo/world.png (512, 512, 3)`.

**SHA256 of the regenerated file vs. the file already committed at this
session's start (backed up before running):**
```
regenerated: 5da5c2d853ac559f6c8ae7f35ebe42a155e81e6bb5bb9c6ab66fb7ace7ecc06a

```
`git status --short demo/world.png` shows no diff after the run, confirming the
match independently of the hash script. **This is a genuine, positive,
empirically-verified result**, not an inference: `demo/world.png` regenerates
byte-for-byte from `demo/receipts/small` (committed) plus `render_world.py`
(committed), because the script hardcodes `seed=7` directly in its own source
(`demo/render_world.py:35`, `thrml_sample(prog, n_chains=8, n_samples=60,
n_warmup=1200, steps_per_sample=4, seed=7)`) and the per-cell decoration is
itself deterministically seeded on `(row, col)`
(`np.random.default_rng(r*1000 + c)`, `render_world.py`'s tail).

**What this does NOT establish, stated precisely, per this task's own
"UNAVAILABLE" discipline:**

- `demo/world_elevation.png` (`demo/elevation_world.py:154,189,250-264`) and
  `demo/world_layer1.png`/`world_stacked.png` (`demo/stacked_world.py:113,157`)
  are generated by scripts that **structurally follow the identical
  hardcoded-seed pattern** (`seed=7`, `seed=8`, `seed=100+i`, all literal
  integers in source, confirmed by reading each script) -- but these three were
  **not independently re-run and hash-checked this task**, for time. Their
  reproducibility is therefore `UNAVAILABLE: pattern strongly suggests the same
  result as world.png, but not independently verified by re-running -- do not
  cite as confirmed`.
- `demo/world_multi.png`/`world_free.png` (`demo/multichunk.py:332,491,636,716`)
  pass a `seed` **variable**, not a literal, to their sampling calls. This
  task did not trace that variable back to its origin (fixed constant, CLI
  argument with a default, or a `random.randint` call) in the time available.
  Reproducibility for these two figures is `UNAVAILABLE: seed origin not
  traced this task`, not confirmed either way.
- **No test in the repository checks that any committed `world*.png` still
  matches a fresh render of its generating script.** `grep -rln "world\.png"
  tests/*.py` (and the equivalent for every sibling PNG) returns nothing. If
  `render_world.py`'s rendering/decoration code changed in a future edit
  without also re-running it, the committed PNG would go stale silently --
  nothing would fail, because nothing checks.

## Provenance finding, discovered while running this task's own reproducibility tests: the receipt directory is not actually frozen

**`demo/receipts/small/simulation.json` is a git-tracked, committed file that
`simulate()` overwrites, unconditionally, every time the CLAMPED sampling path
runs** (`src/tsu/simulate.py:199-200`: `out_path = d / "simulation.json";
out_path.write_text(json.dumps(doc, indent=2))`) -- and there is no
`.gitignore` entry for it (`grep -n "simulation\|receipts" .gitignore` finds
nothing). It sits in the exact same directory as `program.json`,
`verification.json`, `passes.json`, `gates.json`, `target.json` -- files that
genuinely ARE frozen at compile time and never rewritten by sampling. Nothing
distinguishes, to a reader of the directory listing, which files are permanent
compile-time evidence and which one is scratch state from whoever last ran a
clamped draw. **Concrete demonstration, not a hypothetical:** this file was
already showing as modified in `git status` before this audit wave began
(from Phase A's own `trace_runtime.py` run), was further overwritten by this
task's own `R1.md`/`R17.md` test scripts (most recently to
`{"n_chains": 6, "n_samples": 3, "n_warmup": 600, "steps_per_sample": 4,
"beta": 1.0, "seed": 999}`), and would be overwritten again by the next person
who simply runs the live app and pins one cell. **This directly undercuts the
"given a receipt ... " framing of this very task's own brief**: a "receipt" in
this codebase is not the immutable, load-once artifact the PIPELINE panel's own
language ("compiled once, at load") implies for the *compile* side -- one file
inside it is mutable session state that happens to be tracked in git. Per this
task's Global Constraints ("do NOT repair"), this file is deliberately left out
of this wave's commit, exactly as prior audit rounds did, rather than reset --
see the commit for confirmation.

## Findings

### Critical

**RP-1: A tracked, committed file inside the "receipt" directory
(`demo/receipts/small/simulation.json`) is silently overwritten by ordinary use
of the live app's clamped path, with nothing in the codebase or the file
system distinguishing it from the genuinely frozen compile-time evidence it
sits alongside.** See the provenance finding above for full detail and the
concrete git-history demonstration. **Concrete failure scenario:** two
engineers each run the app, each pin a different cell, each unknowingly
overwrite `simulation.json` with their own session's draw; if either commits
the receipt directory afterward (nothing marks the file as scratch/output),
the repository's history of "the" simulation result for this receipt becomes
whoever committed last, with no audit trail distinguishing a deliberate,
documented simulation run from an accidental one. **What was checked:** `git
log --oneline -- demo/receipts/small/simulation.json` (3+ unrelated commits
touch it, none of their messages mention it as their purpose); `.gitignore`
grepped for `simulation`/`receipts` (no entry); `src/tsu/simulate.py:199-200`
read directly to confirm the unconditional write; reproduced the overwrite
live, twice, this task (TEST A/B above and the R1 sentinel run both left their
own `seed`/`params` in the file). **Severity raised to Critical, above R17's
other findings, because it is the one finding in this wave that actively
compromises the audit's own evidentiary record** (this audit's own test runs
are now indistinguishable, in the tracked file, from a real user's session) --
not merely a documentation or labelling gap like the rest of this section.

### Important

**RP-2: The session's initial `seed_base` is never logged, asymmetrically with
every later reseed.** See Test 2 above for full detail
(`demo/lattice_app.py:2170` vs. `:4451-4454`/`:4489-4492`). Concrete failure
scenario and what was checked are given in full above; not repeated here.
**Severity: Important** -- narrower than it first appears (the per-draw `seed`
that actually matters for `worldfile.save_world` is unaffected), but a real,
user-visible gap in a design goal (the log panel) the app otherwise meets for
every other reseed event.

**RP-3: No committed figure has a test (or any mechanism) verifying it still
matches a fresh render of its own generating script.** See Test 3 above.
**Concrete failure scenario:** a future edit to `render_world.py`'s shading
constants, palette, or decoration algorithm would silently desynchronise
`demo/world.png` from what the current code actually produces, and nothing --
no test, no CI check, no doc comment -- would catch it; the PNG would keep
looking authoritative. **What was checked:** `grep -rln "world.*\.png"
tests/*.py` across the whole `tests/` directory -- zero hits for any of the six
committed world PNGs.

### Minor

**RP-4: `demo/render_world.py` (and `elevation_world.py`, `stacked_world.py`)
have no `if __name__ == "__main__":` guard -- their entire sampling-and-render
sequence executes unconditionally at import time.** Confirmed by reading
`render_world.py` top to bottom (module-level code, no guard, ending in
`Image.fromarray(...).save("demo/world.png")` as the last line of the module
body). **Currently harmless**: confirmed by grep
(`grep -rln "import render_world\|from render_world" demo/*.py src/tsu/**/*.py
tests/*.py`) that nothing in this repository imports `render_world` as a
module today -- the one apparent hit (`demo/multichunk.py:42`) is prose in a
comment, not an import statement, checked by reading that line directly. **Why
it is still worth recording:** if any future module ever imported
`render_world` for one of its helper functions, that import would silently
resample 480 draws and overwrite `demo/world.png` as a side effect no import
statement should have. **What was checked:** full read of `render_world.py`;
grep for every import site of the three world-rendering scripts across
`demo/`, `src/tsu/`, and `tests/`.

### What was tried and did not turn up a finding

- Attempted to find any source of cross-process nondeterminism in the sampler
  beyond the explicit `seed` argument -- checked `thrml_backend.sample_chains`
  for any other entropy source (`time.time()`, `os.urandom`, unseeded
  `random.random()`, hash-based iteration over an unordered `set`/`dict`
  affecting numerical results) by reading the function in full
  (`src/tsu/backends/thrml_backend.py:181-224`): the only randomness is
  `jax.random.key(seed)` and its `jax.random.split` descendants, all seeded
  from the one caller-supplied integer. TEST B's cross-process byte-identical
  result is the empirical confirmation this reading predicts. No finding.
- Checked whether `PYTHONHASHSEED` or any other process-level environment
  variable affecting `dict`/`set` iteration order could leak into the sampled
  result (a classic hidden-nondeterminism source in Python) -- grepped
  `demo/*.py`/`src/tsu/**/*.py` for `PYTHONHASHSEED`, `hash(`, iteration over
  a bare `set(...)` in a code path that reaches the sampler; the two
  subprocess runs in TEST B used the SAME interpreter binary with default
  (unset, therefore randomised per-process) hash seeding and still agreed
  byte-for-byte, which is itself evidence hash randomisation does not leak
  into the sampled result on this code path. No finding.
- Checked whether `reconstruct_program`/`encode()` (the deterministic
  name-mapping re-derivation A1's Finding I-2 already flags as re-running
  live) could be a HIDDEN source of cross-run divergence if it were ever
  non-deterministic -- TEST A/B's `IsingModel` weights/biases equality check
  (not just the final draws) directly confirms this path reproduced
  identically too, both within and across processes. No finding.
