# R16 -- Duplication vs canonical source

**Scope.** Every place `demo/` re-implements something `src/tsu`, thrml, or torx
already provides. For each: legitimate independent oracle, or accidental drift?
A1 already found one instance (I-1, double codeword-test/decode/validate on the
clamped path); this task verifies it independently, sharpens one detail A1's
prose glossed over, and searches for more.

**Method.** Grepped `demo/*.py` for every plausible reimplementation surface:
energy formulas, `is_codeword`/`decode`/`validate`, sigmoid/autocorrelation/ESS
math, the mediator gadget's `arccosh` formula, and every hardware-cap constant
(`max_abs_coupling`/`coupling_cap`/`field_cap`/`node_budget`). Every hit was read
in full at its definition site, not just at the grep line, and cross-checked
against the canonical `src/tsu` function it claims to reuse or duplicate.

## Confirmed: I-1, re-verified and sharpened

**A1's finding, re-verified independently.** `src/tsu/simulate.py:157-169`
(inside `simulate()`) and `demo/lattice_app.py:1238-1255` (`classify_draw`, one
call per row from `_run_clamped_batch`) each independently call
`enc.is_codeword`, `enc.decode`, and `spec.contract.validate` on every row of the
same returned array. Confirmed again this task by direct reading of both call
sites (not merely re-quoting A1's trace counts): both bodies are structurally
identical three-call sequences over the same `got`/`rows` array, in the same row
order.

**One detail worth sharpening, because it changes the risk profile slightly from
how A1's prose states it.** A1's finding describes this as "both call sites use
the compiler's own canonical `enc`/`spec.contract`" -- read literally, that could
mean the SAME `Encoded`/`Spec` object is being read twice. It is not.
`simulate()` builds its own, freshly-constructed `enc` and `spec` locally
(`src/tsu/simulate.py:127-129`: `spec = load_spec(...); enc = encode(spec,
encoding)`), while `classify_draw` uses `receipt.enc`/`receipt.spec.contract`,
built once at `Receipt.__init__` (`demo/lattice_app.py:1129`) from the SAME
`spec.yaml` file and the SAME `encoding` string, via a SEPARATE call to the
identical canonical `encode()` function. **These are two independently-typed
constructions of value-equal objects, not one object read twice.** Because
`encode()` is documented and (elsewhere in this audit, A1 Finding I-2) confirmed
to be a pure, deterministic function of its two arguments, the two `Encoded`
instances are guaranteed equal today -- so this does not change A1's verdict
(legitimate reuse of the canonical *function*, not a correctness bug) -- but it
does mean the duplication is real construction-time duplication (two calls to
`encode()`'s full linear-form rewriting machinery, not two reads of a cache),
which is the SAME cost A1's own Finding I-2 already flags for `Receipt.__init__`
alone. **Severity unchanged from A1 (Important); recorded here because R16's
brief is specifically to judge "legitimate independent oracle, or accidental
drift," and the honest answer needs the precise mechanism, not the approximate
one.**

## New finding: `demo/layers.py`'s `FIELD_CAP` is a hand-copied literal, not a read of the canonical source

**`demo/layers.py:56`**: `FIELD_CAP = 6.0` -- a bare module-level float
constant. Its own docstring (`layers.py:34-38`) says plainly where it came from:
*"`FIELD_CAP` (\|b\| <= 6.0) is an ASSUMED project working value carried over
from demo/receipts/small/target.json's own `max_abs_coupling` entry ... not a
sourced Extropic figure here either."* "Carried over" means exactly what it
sounds like: a human copied the number out of a JSON file into a Python literal
at some point. It is used as `bias_patch`'s default `field_cap` parameter
(`layers.py:63-65`) and passed explicitly at `demo/lattice_app.py:4313`
(`field_cap=FIELD_CAP`).

**This is accidental-drift risk, not a legitimate independent oracle**, and the
codebase itself demonstrates the correct alternative right next to it:
`demo/frontier.py`'s `headroom_from_receipt` reads the SAME kind of gate value
"straight from gates.json -- what the `gate_checks` pass actually evaluated"
(`frontier.py:134-149`), and the module's own docstring states the general
principle this project otherwise follows: *"gates.json / from `tsu.target.Z1`,
never hardcodes them"* (`frontier.py:37`). `layers.py`'s `FIELD_CAP` is the one
place found this wave that violates that stated project norm -- every other cap
display site this audit read (`frontier.py`, the VERIFICATION panel's gate rows,
`demo/lattice_app.py:2974-3002`) reads `gates.json`/`target.json` live, never a
literal.

**Concrete failure scenario, and why it is not hypothetical:** `audit/provenance.md`
Finding P-3 (Phase A, this same audit) already establishes that
`TargetProfile.max_abs_coupling` -- the field `layers.py`'s docstring says
`FIELD_CAP` was "carried over from" -- must be split into two fields
(`max_abs_coupling` for `\|J\|`, a new `max_abs_bias` for `\|b\|`) in Phase F,
because `\|J\|`'s cap is now `EXTROPIC-DOCUMENTED FACT` (6.0, citable) while
`\|b\|`'s stays `PROJECT ASSUMPTION` (also currently 6.0, but unsupported). When
that schema change lands, `layers.py:56`'s hardcoded `6.0` will not
automatically track whichever field becomes the real source of truth for
`\|b\|` -- it will keep returning `6.0` regardless of what `target.py` says,
silently, because nothing wires it to read the live value. **This is exactly
the drift this task's brief asks about, and it is scheduled to become live risk
by the same audit's own already-queued Phase F fix**, not a remote possibility.

**What was checked:** `grep -n "FIELD_CAP" demo/layers.py demo/lattice_app.py
tests/test_layers.py` -- three use sites, all consistent with the constant
being self-contained and never re-derived from `target.json`/`gates.json` at
runtime; `tests/test_layers.py:62`'s own sanity check (`assert base_bmax <
FIELD_CAP`) imports the SAME constant from `layers.py`, so it pins `FIELD_CAP`
against itself, not against the canonical `target.py` value -- a test that
could not catch this drift even if it happened, because both sides of its
assertion trace back to the one hardcoded literal.

**Severity: Important** (real drift risk, timed against an already-planned
schema change in this same audit's own fix queue; not a present correctness
error -- the value is correct today).

## New finding, minor: a documented-but-worth-noting triple reimplementation of the core energy formula

`E(x) = offset - b.s - s^T J s` (spins `s = 2*occupancy - 1`) is independently
typed **three times**, deliberately, each time to avoid importing a
leading-underscore name across a module boundary:

| Copy | Location | Own docstring's stated reason |
|---|---|---|
| `energy_of_draw` | `demo/lattice_app.py:1072-1086` | *"reimplemented here ... rather than importing a leading-underscore name from another module"* |
| `_from_ising` | `src/tsu/passes/search.py:743-750` | (no docstring; the compiler's own internal copy, used by `_measure_mixing` for the receipt's frozen `ess`) |
| `_energy_of` | `demo/ess_run.py:82-91` | *"reimplemented locally below ... to avoid importing a leading-underscore name from another module ... the identical formula demo/lattice_app.py's energy_of_draw also carries, for the same reason"* |

All three were read in full and confirmed algebraically identical (`total =
offset; total -= sum(b_i * s_i); total -= sum(J_k * s_u * s_v)` in every copy,
modulo cosmetic differences in how the subtraction is written). **This is a
deliberate, well-documented pattern with a real reason** (avoiding a
private-name cross-module import), not accidental drift in the sense of "nobody
noticed" -- each copy's own docstring names the other two by file. It is
recorded as a Minor R16 finding anyway because the safety net is incomplete:
`tests/test_frontier.py:287` pins `energy_of_draw` against a hand-computed
value, but **no test anywhere cross-checks `energy_of_draw`, `_from_ising`, and
`_energy_of` against EACH OTHER on the same live draw** (`grep -n
"energy_of_draw\|_from_ising\|_energy_of" tests/*.py` finds exactly two test
functions, `test_frontier.py:287` and `test_ir.py:20`'s unrelated hand-computed
assignment -- neither cross-checks across modules). Three independently-typed
copies of one formula, with the only test coverage anchored to one of the three
against a hand value, is exactly the shape of duplication that could silently
diverge if any one copy were "fixed" in isolation -- and per this audit's own
R3 task (Wave 2, not yet run), a live cross-check of `energy_of_draw` against
the compiler's own energy and the independent oracle is already mandatory
there; this finding notes that `_from_ising`/`_energy_of` are not included in
that mandate and probably should be, since they are the same formula reused for
the receipt's own frozen mixing diagnostic and for `demo/ess_run.py`'s honest
ESS measurement respectively -- both trustworthiness-relevant computations.

**Severity: Minor** (deliberate, documented, algebraically verified identical by
reading; the gap is in cross-module test coverage, not in present correctness).

## What was checked and found to be the GOOD pattern, not drift

- **`is_codeword`/`decode`/`spec.contract.validate` reuse across every other
  `demo/` module that touches a raw draw** -- `demo/render_world.py:20-43`,
  `demo/seam_check.py:5-68`, `demo/multichunk.py:41-305`,
  `demo/stacked_world.py:82-161`, `demo/elevation_world.py:10-193` all call the
  canonical `enc.is_codeword`/`enc.decode`/`spec.contract.validate` trio
  directly, each with an explicit "reuse, not reimplementation" comment at the
  top of the file. No hand-rolled decode or contract-check logic found anywhere
  in `demo/`. This is the dominant pattern in this codebase, and it is the
  correct one.
- **`demo/scope.py:147`'s `autocorrelation`** looked, from the function name
  alone, like a candidate reimplementation of `src/tsu/ess.py:96`'s
  `autocorrelation` -- it is not. Read in full: `scope.py:103` imports
  `tsu.ess.autocorrelation as _chain_autocorrelation`, and `scope.py`'s own
  `autocorrelation` (`:147-158`) is a thin, explicitly-labelled adapter
  (*"Delegates to `tsu.ess.autocorrelation` -- see module docstring for why
  this is a reuse, not a reimplementation"*) that calls `_chain_autocorrelation`
  and slices/validates its output. This is the function A2's Finding C-1 traced
  `render_acf_plot` to (`lattice_app.py:1538`) -- C-1's problem is what series
  gets fed into this call, never a duplicated implementation underneath it. No
  R16 finding here.
- **`demo/frontier.py`'s gate headroom** (`headroom_from_receipt`,
  `frontier.py:133-162`) reads `gates.json` fresh every time, never hardcodes a
  cap -- confirmed by its own docstring's explicit claim and by reading the
  function body, which takes `gates: list[dict]` as a parameter rather than a
  module constant. This is the pattern `layers.py`'s `FIELD_CAP` should have
  followed and did not (see finding above).
- **`demo/scope.py:229`'s `sigmoid`** -- a bare one-line `1/(1+exp(-x))`. Checked
  whether `src/tsu` carries an equivalent this should delegate to instead
  (`grep -rn "def sigmoid\|1.0 / (1.0 + np.exp" src/tsu`) -- no match anywhere
  in `src/tsu`; this is a textbook closed-form with no compiler-side canonical
  implementation to drift from. No finding: there is no "canonical source" this
  duplicates.
- **The mediator gadget's `A = arccosh(...)` formula** -- checked whether it
  appears anywhere outside `src/tsu/passes/route.py`/`lower.py` (`grep -rln
  "arccosh\|acosh" demo/*.py src/tsu/**/*.py`) -- it does not; the only two
  hits are the defining module (`route.py`) and its consumer (`lower.py`,
  reading the mediator identity `route.py` produced, not recomputing the
  formula itself). No finding.
