# R4 -- Sampling semantics (Wave 2)

**Method:** re-derive Phase A's already-filed Critical finding (`truth_table.md`
C-1: the live SCOPE panel's `tau`/ACF plot runs `tsu.ess`'s Sokal estimator
over a series that is not a Markov-chain trajectory) independently, from two
directions -- (1) a fresh, unabridged reading of the exact call chain
(`render_acf_plot` -> `thrml_backend.sample`/`sample_chains` -> the sampler
worker), not merely re-quoting A2's own citations, and (2) a live,
**numeric** reproduction of the defect on real sampler output from the same
code path the app uses (`audit/r4_sampling_semantics_check.py`, run with the
project's pinned interpreter, output reproduced below). Then determine the
full blast radius: every other statistic the live app currently displays,
checked for the same category of defect.

## Confirmation of C-1 -- independent, not inherited

Direct reading (not re-quoting A2) confirms every load-bearing fact C-1
depends on:

- `render_acf_plot` (`demo/lattice_app.py:1519-1584`) imports
  `integrated_autocorrelation_time` **directly** (`:80-81`), never
  `effective_sample_size` -- confirmed by `grep`: `effective_sample_size`
  does not appear anywhere in `demo/lattice_app.py`. `tsu.ess`'s own
  reliability gate (the `N/tau < RELIABILITY_MIN_N_OVER_TAU` -> `ess=None`
  logic, `ess.py:189-242`) therefore **cannot fire** on this code path at
  all -- it is not merely bypassed for this instance, it is never even
  reachable from `render_acf_plot`.
- `energy_trace.ys` (fed to `render_acf_plot` as `series`, `:3327,3354`) is
  a single flat `Trace` (`lattice_app.py:1040-1068`), appended to once per
  `_handle_msg` call (`:3458`) in strict arrival order, with **no
  chain-boundary metadata of any kind**.
- Unclamped path (`_run_unclamped_tick`, `:1401-1424`): every tick calls
  `thrml_sample` (== `thrml_backend.sample`) with a **fresh seed**
  (`seed = self.seed_base + self.draw_counter`, `:1405`) and the fixed
  `n_warmup=300`. `thrml_backend.sample_chains` (`:181-229`) draws a fresh
  `jax.random.key(seed)`, splits it per-chain, and calls
  `jax.random.bernoulli(0.5, ...)` for the initial state (`:224-225`,
  "uniform-random init, NOT hinton_init") -- there is no module-level or
  object-level chain-state variable anywhere in `thrml_backend.py` for this
  to persist in even if it wanted to.
- Clamped path (`_run_clamped_batch`, `:1426-1454`): `simulate()` ->
  `thrml_backend.sample` -> `sample_chains(...).reshape(-1, ...)`
  (`simulate.py:151`, chain-major flatten) -- `CLAMP_N_CHAINS=6`
  mutually-independent parallel chains' worth of samples end to end, with a
  hard discontinuity every `n_samples` rows the flat series carries no
  marker for.

## Numeric reproduction (not merely a reading)

`audit/r4_sampling_semantics_check.py` builds a 6-spin ring model
(`beta=2.0`, so there is genuine per-chain autocorrelation structure to
measure at all) via `lower`/`analyse`/`build_program` (no `place`/`route`/
`compile_spec`), then calls the **real** `tsu.backends.thrml_backend.sample`/
`sample_chains` -- the exact functions `demo/lattice_app.py` imports as
`thrml_sample`.

**1. Chain persistence between calls:** two calls to `sample_chains()` with
identical `(prog, seed, n_chains, n_samples, n_warmup, steps_per_sample)`
produce **bit-for-bit identical output** (`identical=True`). This is a pure
function of its arguments -- confirms empirically, not just by reading, that
no hidden module-level chain state persists between calls (a real risk this
audit was obligated to actually test, not assume from a docstring).

**2. Successive draws within one unclamped tick, `n_chains=6`:** shape
`(6, 1, 6)` -> flattened `(6, 6)`, exactly what gets pushed row-by-row into
`energy_trace`. Each row is drawn from an independently-seeded, independently
-warmed-up parallel chain contributing exactly one sample -- there is no
"later in the same trajectory" relationship between any two of the six rows
from a single tick, let alone between ticks.

**3. Reproducing C-1's number, side by side:**

| shape fed to `tsu.ess` | tau | window | window_saturated | reliability verdict |
|---|---|---|---|---|
| (A) correct `(n_chains=8, n_samples=400)`, through `effective_sample_size` | -- | -- | -- | `reliable=False`: `N/tau=3208 (N=3200, tau~=1.00)` below the 5000 threshold |
| (B) **chain-major-flattened** `(1, 3200)` -- what `render_acf_plot` actually computes | **0.9868** | 6 | False | *(no gate reachable at all, see below)* |
| (C) same draws, correctly shaped `(8, 400)`, `integrated_autocorrelation_time` directly (bypassing the gate, for comparison only) | 0.9976 | 5 | False | *(not displayed anywhere in the live app)* |

(B) and (C) are **different numbers** computed from the same underlying
draws (0.9868 vs 0.9976) -- on this particular instance the gap is small
because the ring model mixes fast at `beta=2.0` (correlation dies off within
a handful of sweeps regardless of how the series is shaped), but the two
numbers are not the same statistic and are not guaranteed to stay close in
general; a slower-mixing model would separate them further. **(B) is
precisely what a viewer of the live SCOPE panel sees as `"tau~1.0"` with a
marked vertical line; (C) -- the only one of the two `tsu.ess`'s own module
docstring sanctions as a valid input shape -- is never computed anywhere in
the live app**, only in `demo/ess_run.py`, a separate script the SCOPE panel
never calls.

## A previously-understated mitigating fact, and why it does not change the verdict

`render_acf_plot`'s caption (`:1573-1583`) **does** compute and display a
reliability readout, using the same shared constant `tsu.ess` uses:
`reliable = n_over_tau >= RELIABILITY_MIN_N_OVER_TAU` (imported directly
from `tsu.ess`, `:80-81`), printed as `"reliability threshold
(tsu.ess.RELIABILITY_MIN_N_OVER_TAU)=5000: MET/NOT MET"`. This is a more
honest self-report than A2's C-1 write-up emphasized ("displays a
confident-looking `tau~X.X` number regardless" is true of the headline
number and the vertical marker line, but the caption text right below it is
not silent about reliability).

This does **not** rescue the finding, for two reasons confirmed above:

1. The headline number and the vertical marker line are drawn **unconditionally**
   once `len(series) >= 12` (`:1533`) -- the MET/NOT MET readout is smaller
   caption text below the plot, not a gate on whether the number/line
   render at all. A viewer glancing at the plot (the marked line is the
   most visually salient element) gets an actionable-looking number
   regardless of what the caption says.
2. More fundamentally: `N/tau >= 5000` is a check on whether a **valid
   single-chain series** is *long enough relative to its own tau* -- it
   assumes its input already is one chain's trajectory. It cannot detect,
   and was never designed to detect, that the input is not a chain at all.
   A sufficiently long run under this exact defect could accumulate enough
   draws to read `"MET"` while the number remains physically meaningless,
   because reliability-by-sample-count and validity-of-input-shape are
   orthogonal questions, and only the second one is actually wrong here.

## Findings

### Critical (confirming Phase A's C-1, independently re-derived and numerically reproduced)

**C-1 (confirmed independently): the SCOPE panel's live `tau`/ACF readout
computes Sokal's estimator over a flat series that concatenates independent
restarts and independent parallel chains, with `tsu.ess`'s own reliability
gate never reachable from this code path at all.** `demo/lattice_app.py:1519-1584`
imports `integrated_autocorrelation_time` directly, never
`effective_sample_size`. **Concrete failure scenario:** a viewer watches the
SCOPE panel at Full speed (multiple parallel chains per tick, or a clamped
batch with `CLAMP_N_CHAINS=6`), sees `"tau~1.0"` (or any value) marked with
a vertical line and a caption reading `"reliability threshold ... MET"`
once enough draws accumulate, and reasonably concludes this is a validated
measurement of how many samples the sampler needs between independent
draws. It is neither: the number is computed on data that categorically
cannot support the estimator (see numeric reproduction above), and the
"MET" readout cannot detect that category error because it only checks
sample-count-relative-to-tau, never chain validity. **What was checked:**
full independent re-reading of the exact call chain (not re-quoting A2);
live numeric reproduction on the real sampler entry point,
side-by-side against the correctly-shaped computation on the identical
underlying draws; the mitigating "MET/NOT MET" caption text, read in full
and shown not to gate the display. **Recommended scope for Phase F (not
performed here):** either gate the number/line behind a genuine
`(n_chains, n_samples)` buffer collected within one `sample_chains` call
(the pattern `demo/ess_run.py` already implements, unused by the live
panel), or relabel the plot to state plainly what it measures and drop the
`tau` claim entirely.

### Important

**I-2 (new): the raw energy trace line plot (`_draw_trace`, energy canvas,
x-axis `"sweep"`) draws one connected polyline through draws that are not a
single evolving trajectory, visually implying continuous dynamics that do
not exist.** `demo/lattice_app.py:3285-3314`, called with `self.energy_trace`
at `:3223` and `:3512` -- `canvas.create_line(*pts, ...)` connects every
point in `trace.xs`/`trace.ys` in arrival order with a single line, labelled
`xlabel="sweep"` (`:3223`). The underlying series is the exact same
chain-concatenated, restart-interleaved sequence C-1's own analysis
established `energy_trace` to be. **Concrete failure scenario:** a viewer
watches the connected line jump between values and reasonably reads it as
"the system's energy evolving over successive sweeps," including across a
hard discontinuity where one independent chain's last sample is connected
by a straight line segment to a completely unrelated chain's first sample
(e.g. between chain 0's 3 samples and chain 1's 3 samples in a clamped
batch, or between one tick's fresh restart and the next). Unlike C-1, this
is a **raw display**, not a derived statistic asserting a specific number
(no `tau~X.X`-style claim is attached to it) -- which is why this is filed
Important rather than Critical -- but the x-axis label `"sweep"` and the
connected-line rendering both actively suggest a continuity the data does
not have. **What was checked:** `_draw_trace`'s full implementation
(`:3285-3314`); confirmed it draws one unbroken `create_line` through
every point with no gap/marker at a chain or restart boundary; cross-checked
against the same chain-boundary facts C-1's own analysis already
established for `energy_trace`'s construction. **Recommended scope for
Phase F:** either break the line at a recorded chain/restart boundary
(scatter points instead of a connected line, or a visible gap), or rename
the x-axis away from `"sweep"` (which implies one system's own MC time
axis) to something order-neutral like `"draw #"`.

### What was tried and did not turn up a finding

- Checked `magnetization_trace`/`raw_draws`-derived statistics
  (`magnetization`, `energy_histogram`, `per_cell_occupancy`) for the same
  category of defect, empirically (not just by reading `scope.py`): ran the
  real sampler, shuffled the chain-major-flattened draws, and confirmed
  each statistic's output is identical (magnetization: sorted-value
  equality; energy histogram: identical bins/counts) whether the draws are
  in chain-major or shuffled order. These statistics have no notion of
  "order" to violate -- confirmed, not merely asserted. No finding.
- Checked whether the VERIFICATION panel's `ess`/`diversity_*` fields
  (frozen, compile-time) share `energy_trace` with the live SCOPE panel in
  any way: they do not -- `_verify`/`_measure_mixing` run once, at compile
  time, on their own genuinely-shaped `(32, 200)` sample array
  (`search.py:513-514`), entirely independent of the live session's own
  draws. This is A2's own M-2 finding (juxtaposition confusion), a
  different issue from C-1; not re-filed here.
- Checked whether `sample_chains`/`sample` carry any hidden persisted state
  between calls that could make "successive draws" less independent than
  the code reads: two calls with identical arguments produce bit-for-bit
  identical output (a pure-function property, confirmed empirically, not
  assumed). No finding -- the independence problem is entirely in how
  `lattice_app.py` *uses* fresh seeds/fresh warmups every tick, not in any
  hidden coupling between calls.
- Checked `n_chains`/`n_warmup`/`steps_per_sample` against A2's own table
  for drift: independently re-confirmed by direct reading of
  `_run_unclamped_tick`/`_run_clamped_batch` (`lattice_app.py:1401-1454`)
  that `N_WARMUP=300`/`CLAMP_N_WARMUP=600` and `STEPS_PER_SAMPLE=4` are the
  fixed module-level constants used unconditionally at every speed level;
  A2's own M-1 finding (the pinned `n_chains/call` line reading as
  speed-dependent when it is a constant) is not re-litigated here.
